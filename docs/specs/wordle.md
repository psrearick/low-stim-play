# Wordle — Build Spec

Ships under the display name **"Five Letters."** "Wordle" is NYT Games' trademarked
name — same category as Boggle/Yahtzee/Family Feud/Quartiles/Apples-to-Apples, all
renamed to a generic display name before shipping (see `docs/DEVLOG.md`'s "Game
renaming" section). Chosen collaboratively the same way those were: proposed alongside
"Word Guess"/"Letter Logic," user picked "Five Letters." Internal identifiers
(`GameType::Wordle`, `wordle` routes/DB values) keep the real mechanic name, same
rationale as every other renamed game — none of that is user-facing. See `docs/TODO.md`
#10.

---

## 1. Core design decision (read first)

Solo, one secret word, six guesses, letter-by-letter feedback — the simplest and lowest-
risk of the five games in `docs/TODO.md` #10. No hidden multiplayer state (unlike Best
Match/Clear the Deck), no spatial/adjacency puzzle to generate (unlike Boggle/Word
Blocks/Strands below), and no semantic content to author (unlike Connections/Strands,
which need real thematic categories rather than a word picked at random). The one thing
this game needs that nothing else in this app has: a **secret answer that must never
reach the client** — not in a rendered Livewire public property, not in page source,
not in a network payload — until the game actually ends (win, loss, or reveal). This is
a lighter version of the same problem Best Match/Clear the Deck's per-seat secrecy
already solved for a multiplayer room (`docs/DEVLOG.md`'s Best Match/Clear the Deck
sections): resolve the answer fresh from the database/session inside the one action
(`submitGuess()`) that needs it, never assign it to a public property.

Because word selection is a plain pick from an existing dictionary (`storage/app/
words.txt` already has 5,134 five-letter entries — see section 3), this game fits the
existing `DailyPuzzle::seedFor()` zero-persistence model cleanly, the same way Boggle
and Word Blocks already do: no new `puzzles` table, no LLM call, no non-determinism to
work around. Contrast this with Connections/Strands (`docs/specs/connections.md`,
`docs/specs/strands.md`), which likely need actual semantic content generation and may
need to break that pattern.

## 2. NYT rules → this app's equivalents

The core loop (guess a 5-letter word, get per-letter feedback, six tries) is already
fully digital and needs no physical-to-digital translation. What NYT's own version adds
on top is: a curated, non-obscure answer list distinct from a much broader "valid
guess" list; a "hard mode" toggle; and the now-iconic spoiler-free emoji-grid share
text. None of those are inherent to the mechanic itself, so each got its own decision
below.

## 3. Resolved design decisions

- **Word length: classic 5-letter words, 6 guesses.** No open question here — kept
  as-is, matching NYT's own shape; nothing about this app's own constraints calls for
  a variant.
- **Sharing: the existing challenge-link mechanism only, no emoji-grid share text.**
  `GameType::isChallengeable()` (already used by Boggle/Word Blocks) is the only
  sharing surface for v1 — no NYT-style spoiler-free colored-square text. Keeps this
  game's share story consistent with every other puzzle game in the app rather than a
  one-off format.
- **Hard mode: included as a toggle in v1.** Once a guess reveals a letter is correct
  (green) or present-elsewhere (yellow), hard mode requires every subsequent guess to
  reuse that information — a correct letter must stay in its revealed position, and a
  present letter must appear somewhere in the next guess. Rejected at the moment a
  non-conforming guess is submitted (a clear inline error, not a silently-accepted
  guess that quietly wastes an attempt), the same "reject the whole attempt, no state
  change" precedent Clear the Deck's own invalid-play handling already sets
  (`docs/specs/clear-the-deck.md` section 3). A per-game toggle, not account-wide —
  set before the first guess of a given game and locked once guessing starts, so a mid-
  game switch can't retroactively invalidate already-made guesses.
- **Duplicate-letter feedback: NYT's own two-pass evaluation.** Exact-position matches
  are resolved first and claim their letter from the answer's available pool; only then
  are non-exact guessed letters checked against whatever's left, so a guess that
  over-repeats a letter the answer only contains once doesn't over-credit it as
  "present" more times than it actually appears. Not a design choice so much as a
  correctness requirement — called out here so it's implemented deliberately rather
  than accidentally with a naive per-letter check.
- **Answer list: a new curated "common word" subset, generated by a reusable service —
  not scoped to this game alone.** `storage/app/words.txt`'s 5,134 five-letter entries
  remain the full valid-*guess* list (anything real is accepted, matching NYT's own
  broad guess dictionary), but the daily/random *answer* is drawn only from a smaller,
  common-word-filtered subset of it — this app's Wordle answer is the entire puzzle,
  unlike a Word Blocks/Boggle find among many, so an obscure answer is a much bigger
  quality problem here than the "no frequency data" trade-off `docs/specs/quartiles.md`
  already accepted for Word Blocks was.
  - **New shared infrastructure, not a Wordle-only filter.** Per explicit direction:
    the same commonness-filtering approach is meant to be reused for Word Blocks' own
    answer-word selection later (the 5 words it splits into fragments,
    `docs/specs/quartiles.md`'s `PuzzleGenerator`), and likely for any future word
    game with the same "the target word should read as familiar" concern — so this
    should be built as a standalone, non-game-specific service from day one (e.g.
    `App\Services\Words\CommonWordFilter` or similar, living alongside — not inside —
    `Wordle\AnswerPicker`), not coupled to Wordle's own namespace.
  - **Data source: a general-purpose English word-frequency corpus, deliberately not
    derived from NYT's own possible-answer list.** Needs sourcing during
    implementation — a plain word → frequency/rank dataset, freely redistributable
    (public-domain or permissively licensed), bundled as a new `storage/app/`
    asset the same way `words.txt` already is. Intersected against the existing
    per-length dictionary (5-letter words for Wordle, whatever lengths Word Blocks
    needs later) with some frequency/rank cutoff to decide "common enough" — the exact
    threshold is a tuning detail to settle once a real candidate corpus is in hand,
    not a blocking decision now.
  - **Word Blocks itself is explicitly out of scope for this change right now** — this
    decision only resolves Wordle's own answer selection; applying the same filter to
    Word Blocks' `PuzzleGenerator` is separate follow-up work once the shared service
    exists, tracked in `docs/TODO.md`.

## 4. Data model

- `GameType::Wordle` (`wordle`) — kept alongside the existing cases in
  `App\Enums\GameType`, `label()` returns `"Five Letters"`.
- `App\Services\Words\CommonWordFilter` — the new shared, non-game-specific service
  from section 3: given a word list and a target length, returns the subset judged
  "common enough" against the bundled frequency corpus. Lives outside any single
  game's own service namespace since Word Blocks is meant to reuse it later.
- `App\Services\Wordle\AnswerPicker` — mirrors `Boggle\BoardGenerator`'s seeded
  `Randomizer`/`Mt19937` pattern for `DailyPuzzle::seedFor()` reproducibility, but
  picks from `CommonWordFilter`'s curated 5-letter subset rather than the full
  dictionary; the full `storage/app/words.txt` 5-letter set remains the valid-guess
  check, used only to validate what a player is allowed to *type*, never to pick what
  they're trying to *find*.
- `App\Services\Wordle\GuessEvaluator` — implements the two-pass duplicate-letter
  scoring rule (section 3) and the hard-mode conformance check (does a new guess
  reuse every already-revealed correct/present letter correctly).
- `pages::wordle.play` (route `wordle.play`, path `/five-letters`): `guesses` (list of
  past guesses, each with its per-letter result — safe to persist/broadcast, since
  none of it reveals the answer directly), `status` (playing/won/lost), `hardMode`
  (locked once the first guess is submitted). The secret answer is never a public
  property — resolved fresh from the session/DB only inside `submitGuess()`, the same
  "resolve secret state fresh, never assign it to a rendered property" rule Best
  Match/Clear the Deck established for their own hidden state
  (`docs/DEVLOG.md`'s Best Match/Clear the Deck sections).
- `App\Services\Stats\WordleStatsService`, following the existing `statsFor()`/
  `gamesForUser()`/`bestMetrics()` shape: guesses-to-win distribution and win rate are
  straightforward reuses of the existing pattern. **Streak tracking (current/best
  consecutive daily plays) is deferred, not built for v1** — no existing game in this
  app tracks "played every consecutive day," so it needs its own small design pass
  (what breaks a streak — a missed day? a loss counts as a played day?) rather than
  being folded into this spec as a assumed given.

## 5. Accessibility

Same low-stim system as the rest of the app (see `docs/DEVLOG.md`'s "Site-wide design
system & chrome" section): muted palette, no forced sound, respects
`prefers-reduced-motion` (no letter-flip/shake animation, or one that's skipped
entirely under that media query). NYT's own green/yellow/gray tile scheme is a
well-known colorblind pain point; this app's existing rule ("never rely on color alone,"
already applied to Win/Loss coloring and Word Blocks' found-quartile rows) applies here
too — tile state needs a non-color signal as well (e.g. a shape/icon, not just a
background hue). Screen-reader announcement of each guess's result (`aria-live`) is
worth calling out explicitly, since the visual tile grid alone conveys nothing without
it.

## 6. Deliverables for v1

- `GameType::Wordle` (`label()` "Five Letters") + `App\Services\Words\CommonWordFilter`
  (new shared word-frequency corpus asset + filter service, reused by nothing else yet
  but built game-agnostic per section 3).
- `App\Services\Wordle\{AnswerPicker, GuessEvaluator}`.
- `pages::wordle.play` — guess entry (typed or on-screen keyboard), 6-row guess
  history with per-tile color *and* non-color state indicator (section 5), on-screen
  keyboard recoloring per letter's best-known state, hard-mode toggle (pre-game only),
  reveal-the-answer on a loss, win/loss end state. Route `/five-letters`, name
  `wordle.play`.
- Daily-puzzle wiring matching Task 11's existing shape for Boggle/Word Blocks
  (`docs/DEVLOG.md`'s "Boggle"/"Word Blocks" sections): `GameType::isChallengeable()`
  gains a `Wordle` case, `#[Url] $dailyDate` support via `DailyPuzzle::seedFor()`,
  one-play-per-day lock for signed-in users, and a new "Five Letters" link column on
  `pages::daily-puzzles` (today's-puzzle card plus the 30-row archive table).
- `pages::profile.wordle.index`/`.show` + `App\Services\Stats\WordleStatsService`,
  following the existing per-game profile pattern.
- Homepage card, sidebar link ("Five Letters"), `<x-player-stats>` wiring — same as
  every prior game's.
- Test coverage: `App\Services\Words\CommonWordFilter` and `Wordle\{AnswerPicker,
  GuessEvaluator}` unit tests (duplicate-letter scoring including both directions —
  guess over-repeats a letter, answer over-repeats a letter — hard-mode
  accept/reject cases, `CommonWordFilter` actually narrowing a known word list by a
  known frequency cutoff); `pages::wordle.play` feature tests (win, loss/reveal, the
  answer never appearing in any rendered property or Livewire payload before the game
  ends, daily lock behavior); a browser test for the per-tile non-color state
  indicator and on-screen keyboard recoloring, the bug class `CLAUDE.md`'s "Automated
  Browser Testing" section flags a Livewire-only test can't catch.

## Appendix: mechanic summary (this app's own words, not NYT's copy)

A secret 5-letter word is chosen for each game. The player has six attempts to guess it,
each guess itself a valid 5-letter word. After each guess, every letter is marked one of
three ways: in the correct position, present in the word but in the wrong position, or
absent from the word entirely (duplicate letters are resolved so a repeated guessed
letter isn't over-credited beyond how many times it actually appears in the answer). The
game ends in a win the moment a guess exactly matches the answer, or a loss once six
guesses are used without matching.
