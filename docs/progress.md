Two real, previously-invisible bugs found and fixed while doing this pass (both silently broke color/sizing on **every** page using `bg-accent`, `px-*`, etc. — i.e. most of the "everything is sized wrong" complaint that triggered this whole phase):

1. **`@theme { --color-accent: var(--accent); }` silently failed to generate `bg-accent`** (while `text-accent`/`border-accent` worked) — Tailwind v4 only partially resolves utilities from theme tokens that reference *other* runtime CSS custom properties unless the block is `@theme inline { ... }` (see Tailwind's "Referencing other variables" docs). Every `bg-accent`-styled CTA on the site (setup "Start game" buttons, selected option buttons, dashboard/profile primary actions) was silently rendering as the plain surface color instead of accent blue until this was fixed.
2. **Cascade-layer priority, not specificity, decided the fight between the new global `button { ... }`/`input { ... }` rules and Tailwind's own utility classes.** An unlayered custom rule always outranks *any* rule inside a `@layer` (Tailwind's own utilities live in `@layer utilities`) regardless of specificity or source order — so the plain `button {}` element rule was winning over `bg-accent`/`px-6`/etc. on every Tailwind-styled button site-wide. Fixed by wrapping those element-default rules in `@layer base` (Tailwind's own recommended pattern for exactly this), which restores the expected "unless a utility class says otherwise" precedence.

Also worth remembering: a CSS `/* ... */` comment containing the literal substring `*/` anywhere in its own text (e.g. writing "`bg-accent/px-*/etc`" as a comment) closes the comment early and turns the rest into broken real CSS — surfaced as a cryptic `CssSyntaxError: Missing opening (` from Tailwind's compiler pointing nowhere near the actual cause. Bisect by truncating the file at clean `}` boundaries if this recurs.

### Phase 8, round 3: color misuse + two real bugs + guest room access

- [x] 28. **Accent-blue was overused** — `--accent` (the same bright, saturated blue as a selected Boggle die or a found word) had leaked onto page headings (`<x-panel>`'s `<h1>`, stat-card labels, the avatar badge) and onto generic "primary" CTA buttons (passkey sign-in/confirm, "Add a Passkey") that legacy never color-codes at all — legacy's buttons are *always* the same muted `--btn` tone regardless of importance; the only per-instance color legacy ever applies to a button is `option.active`'s **text**, not its background. Added a `--color-bar` Tailwind alias (`text-bar`/`bg-bar`, aliasing `--bar` the same way `--color-accent` aliases `--accent`) for genuine headings/branding, moved every heading-like use to it, and stripped `bg-accent`/`text-accent` off buttons and transient status messages back to plain styling. Left `--accent` only where legacy's own convention actually uses it: Boggle's selected-die/order-badge/`option.active` state, a found word, the controlling Family Feud team, a won game result — i.e. "something notable happened/is selected," never "this is a heading" or "this is the important button."
- [x] 29. Fixed a real display bug on the dashboard: the username line read literally as `@{{ auth()->user()->username }}` on screen. The `@{{` is Blade's own syntax for *escaping* `{{ }}` so it renders as inert text (meant for JS template literals sharing a page with Blade, e.g. Vue) — there's no Vue here, so this just should have been a plain `{{ }}` all along.
- [x] 30. The online-room code was shown in a `.heading`-classed `<div>`, and `.heading` carries `user-select: none` (see `shared.css`) — the code was never selectable, let alone copyable, by design of a class meant for page titles. Replaced with the same readonly-input-plus-`[data-copy]`-button pattern already used for Boggle's async challenge-share link.
- [x] 31. **Guests can now join an online room without an account; hosting one still requires a real account.** This is a real constraint, not a preference: Laravel's private/presence channel authorization *always* authenticates via the guard and has no "let anyone in" option — "the authorization callback is never executed" for an unauthenticated visitor (Laravel's own broadcasting docs, verbatim). There is no way to admit a truly anonymous visitor to a Reverb presence channel. Solved with a throwaway account: `User::createGuest(?string $name)` creates a real `users` row (`is_guest = true`, a `guest-{uuid}@guests.invalid` email nobody can log back into, a random unusable password, `email_verified_at` pre-filled so nothing ever tries to verify it) and logs it in on the spot — both from `boggle-lobby`'s `joinRoom()` (so a name typed in the lobby's optional "Your name" field carries through) and from `pages::boggle.room`'s `mount()` (so arriving via a bare shared room URL, skipping the lobby form entirely, still works). `is_guest` is the actual gate: `createRoom()` `abort_unless(Auth::check() && ! Auth::user()->is_guest, 403)` server-side, not just a hidden button client-side, and the lobby template only shows "Host an Online Room" to a real account. `routes/web.php`'s `boggle.room` route dropped its blanket `auth` middleware entirely in favor of this per-visitor provisioning — a guard on the route can't distinguish "let guests through to auto-provision" from "let anyone through," so the gating had to move into the page itself. `routes/channels.php`'s existing `room.{code}` channel closure needed **no changes** — once a guest is a real (if synthetic) authenticated user, it's indistinguishable from a registered one to the presence-channel layer. `request()->session()->regenerate()` after `Auth::login()` (session-fixation hygiene, matching what Fortify's own login controller does) is guarded behind `request()->hasSession()`, since `Livewire::test()` drives a component directly without the full HTTP kernel's session middleware, and would otherwise throw in tests despite being fine on every real request. Accepted, undocumented-until-now trade-off: guest accounts are never cleaned up automatically, so `users` accumulates one throwaway row per anonymous room join indefinitely — fine at this app's scale, but a real cost if it ever needs to scale up (a scheduled `DELETE WHERE is_guest AND created_at < ...` job would be the fix).

### Phase 8, round 4: Boggle layout fixes + shared-word scoring/coloring

- [x] 32. Two real centering bugs, both from the same root cause: a plain (non-flex) wrapper `<div>` doesn't auto-center a narrower child inside it, even if that child has `items-center` itself — the child just sits at the wrapper's own natural width/position. `pages::boggle.play`'s root element gained `class="flex flex-col items-center w-full"` (previously bare `<div>`), which fixed the post-game "Back to room"/"Back home"/copy-link block being left-aligned instead of centered whenever `#game`'s own content was wider than that block's `max-w-md`. Separately, the room-code input in `⚡game-lobby.blade.php` was `flex: 1` (stretched to fill the row), which centered the *code text* only within its own oversized box, not within the panel as a whole -- changed to a fixed `8ch` width so the input+Copy button sit together as one centered unit instead.
- [x] 33. **Boggle's shared-session (room or async challenge) reveal now shows who found what, and scores only exclusive discoveries.** Previously every shared game just showed the same single-player "words I found" reveal, and scoring was raw per-word points awarded the instant you found something — with no way to know until the reveal whether another participant found the same word too. Now: `GameParticipant.stats['found_words']` persists each participant's full word→points map (previously only the *count* was kept), and `finalizeSharedSession()` (renamed from `rankParticipants()`) recomputes every finished participant's `score` as the sum of only the words *no one else in the session also found* before ranking win/loss/draw -- same self-correcting re-run-on-every-finish pattern the ranking itself already used. The reveal list colors each word by who found it: mine-only (`--accent`), found by 2+ participants regardless of who (`--bar`, "Both/All" in the legend), or one of up to four other individual participants each get their own hue (`--rival-1`..`--rival-4`, new low-chroma OKLCH tokens matching `--accent`'s lightness so nothing reads as louder than the accent color) -- a 5th+ other participant wraps back to `--rival-1` via `% 4`. A word nobody found stays unstyled, same as before. The live in-progress HUD score during play is still raw (as-you-go feedback; you can't know what others will find until they finish) -- only the post-`endGame()` score and reveal coloring use the adjusted, "exclusive words only" accounting. Verified visually (not just via test assertions) by rendering an actual `Livewire::test(...)->html()` reveal fragment against the real board/dictionary in a headless browser: a word both players found rendered in the shared color and was correctly excluded from both scores, while each player's own exclusive words kept full points and their own color.

- **2026-07-29** — End-to-end verification via the actual `docker compose` stack (not just `php artisan test` on the host) surfaced three real infrastructure bugs from Phase 1, all now fixed in `docker/php/Dockerfile` / `docker-compose.yml`:
