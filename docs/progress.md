A naive Livewire port would break this silently and much more severely — every Livewire public property gets serialized into the page's `wire:snapshot` HTML on every request, so holding `$this->questions` as full rows (with `answers`) would leak every hidden answer to anyone opening dev tools, on every single request, not just via a deliberately-hit endpoint like the legacy's own accepted-risk `reveal` action. Fixed by **never storing the `answers` column as a public property at all**: `$this->questions` only ever holds the client-safe shape (`FamilyFeudQuestion::toSafeArray()` → `{id, prompt, answerCount}`, mirroring the legacy function's own `list` action response), and every action that needs real answers (`submitGuess`, `skipQuestion`, `revealManually`, round-end reveal) re-fetches the current question fresh from the database inside that action instead. Confirmed by `tests/Feature/Games/FamilyFeudGameTest.php`'s `not->toHaveKey('answers')` assertion on every entry in `$this->questions` after `startGame()`.
  - Round-end reveal doesn't need the legacy's own network-round-trip-with-fallback logic (`apiCall('reveal', ...).catch(...)`) — since we already hold direct DB access to the same question inside the same PHP process, revealing the remaining answers is just reading the row we already have, with no failure mode to handle.

- **2026-07-29** — End-to-end verification via the actual `docker compose` stack (not just `php artisan test` on the host) surfaced three real infrastructure bugs from Phase 1, all now fixed in `docker/php/Dockerfile` / `docker-compose.yml`:
  1. `pecl install redis` was failing (`phpize`/`autoconf` not found) because the preceding `docker-php-ext-install` step installs its own build toolchain and **removes it again within that same `RUN` layer**; a separate later `RUN pecl install redis` had nothing left to compile with. Fixed by wrapping it in its own `apk add --virtual .build-deps ${PHPIZE_DEPS} && ... && apk del .build-deps`.
  2. `app`, `queue`, and `reverb` each declared their **own anonymous** `- /var/www/html/vendor` volume — anonymous volumes are per-service, not shared, so `composer install` inside `app` never reached `queue`'s or `reverb`'s copy, and both crash-looped forever on a missing `vendor/autoload.php`. Fixed by switching to named, shared volumes (`vendor_data`, `node_modules_data`) referenced by all three services.
  3. Compiled Blade/Livewire view caches under `storage/framework/views/` record the **absolute source path** for staleness checks (`filemtime()`), and that directory was bind-mounted (`.:/var/www/html`) — shared byte-for-byte between the host (`/Users/.../low-stim-play/...`) and the container (`/var/www/html/...`). Running tests on the host, then hitting the same routes through docker (or vice versa), produced `filemtime(): stat failed for /Users/.../storage/framework/views/livewire/views/....blade.php` and pages silently rendering as the default `welcome` view instead of erroring. Fixed the same way as vendor/node_modules: `storage/framework/views` now gets its own named volume (`storage_views_data`) on `app`/`queue`/`reverb`, so host and container maintain independent compiled-view caches that never collide. That volume needs to be seeded as the `nobody` user (php-fpm's configured user) — Docker copies a named volume's initial content from whatever already exists at that path *in the image* the first time it's mounted, so the Dockerfile now does `mkdir -p storage/framework/views && chown -R nobody:nobody storage/framework/views` before that point.
  4. Unrelated to the above but hit while debugging: after `docker compose up -d` **recreates** a service (e.g. `app`, after a `docker-compose.yml`/image change) without also recreating `nginx`, nginx keeps proxying to the old container's now-stale IP (`fastcgi_pass app:9000` resolves the hostname once, not per-request) and returns 502 until `docker compose restart nginx`. Not a bug to fix, just an operational step: **restart (or recreate) `nginx` any time `app` is recreated**, or use `docker compose up -d` for everything at once rather than rebuilding one service at a time.

- **2026-07-29** — Boggle online multiplayer, wired on top of the existing `Room`/`GameLobby` (Phase 5) infrastructure:
  - `GameLobby::startGame()` (generic, game-agnostic — see Phase 5 notes) now also dispatches a **plain, non-broadcast** Livewire event, `room-game-starting`, alongside the existing `RoomGameStarting` Reverb broadcast. Livewire dispatches events page-wide by default, so a parent page hosting `<livewire:game-lobby>` can listen for it and react — this is how Boggle-specific behavior (generating a shared board) gets triggered without `GameLobby` itself knowing anything about Boggle. The distinction matters: the *local* dispatch only reaches the host's own request (only the host can call `startGame()`, so only their page instance ever receives it) — that's what guarantees the board/`GameSession` gets created exactly once, not once per connected player. The *broadcast* (`RoomGameStarting` over the room's presence channel) is what tells every *other* connected player's browser that the room has started, asynchronously, so their own page can pick up the now-populated `game_session_id` and follow along.
  - New `pages::boggle.room` (route `/boggle/room/{code}`, `auth` middleware) hosts a host-only board size/time-limit picker plus the nested `<livewire:game-lobby>`. `onRoomStarting()` (host path, via the local dispatch above) generates the board, creates a `GameSession` (`mode: Online`), attaches it to the room, and redirects the host straight into `pages::boggle.play`. `onRoomStarted()` (every player, via the `RoomGameStarting` broadcast) does the equivalent redirect once the room's `game_session_id` is populated.
  - `pages::boggle.play` gained an optional `#[Url] public ?string $room`. When present, `size`/`minutes`/`seed` are **overridden** from the room's `GameSession.settings` rather than trusted from the query string directly (a player shouldn't be able to change their own board by hand-editing the URL), `endGame()` joins that existing `GameSession` instead of creating a new one, and — since there are now multiple participants to compare — computes each `GameParticipant`'s `result` (`Win`/`Loss`/`Draw`) by re-ranking *all* participants recorded so far against the top score every time someone finishes. This is deliberately simple and self-correcting (each finish re-ranks the current full set) rather than trying to detect "everyone's done" and finalize once — the plan's own spec ("server collects scores, determines winner") doesn't go into enough detail on timing/race handling to justify more machinery than that. `resetGame()` (solo's "New game") is a no-op in room mode; the reveal screen links back to the room instead.
  - Requires an account for **all** participants, not just the host, including for guests who'd otherwise be able to play solo without one: Reverb presence channels authenticate via the app's default guard before the channel callback even runs (`routes/channels.php`'s closure never executes for a guest), so there's no way to admit an unauthenticated user to `room.{code}` at all. Solo play remains guest-friendly; online rooms don't.
  - Test-writing note: testing `pages::boggle.room`'s `onRoomStarting()`/`onRoomStarted()` in isolation (as `tests/Feature/Games/BoggleRoomTest.php` does) skips the *real* trigger path (`GameLobby::startGame()` dispatching to it), so a test simulating "another player learns the room already started" has to set `$room->status = Active` itself first — in production that's already true by the time this code runs, since it only ever runs in response to `GameLobby` having already set it, in the same request.
