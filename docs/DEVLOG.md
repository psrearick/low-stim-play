# Development Log

Everything about how this app came to be built the way it is: the decisions made, what got built, what deliberately deviated from the original plan and why, and the bugs found along the way (including *why* they happened, not just what fixed them). Organized by feature/area, not by when the work happened — within a section, older material comes first so the reasoning still reads in the order it accumulated. See `docs/TODO.md` for what's still outstanding, and `docs/CHANGELOG.md` for a terse, commit-by-commit record of *what* changed without the rationale.

## Origins

The `legacy/` directory contains a static HTML/CSS/JS game suite (Boggle, Yahtzee, Family Feud) built for photosensitive and migraine-prone users. This app is a migration of that suite into a proper Laravel application: user accounts with passkey authentication, game history/stats, and real-time multiplayer via Laravel Reverb, while preserving the low-stim design language (no animation, no flashing, muted low-contrast palette) exactly.

Foundational decisions made before any code was written:
- Custom `docker-compose.yml` (not Sail), with MariaDB + Redis.
- Fortify + `laravel/passkeys` for auth — no Breeze; custom Blade/Livewire views throughout.
- Boggle built first, to validate the architecture (service classes, Room/multiplayer system, stats) before repeating the pattern for Yahtzee and Family Feud.
- Tailwind v4 for styling, with the legacy CSS ported in as real classes rather than reinterpreted as Tailwind utilities (see "Site-wide design system & chrome" below).

## Infrastructure & tooling

- Custom `docker-compose.yml` + nginx config + PHP Dockerfile (`app`, `nginx`, `mariadb`, `redis` services).
- `.env` updates (MariaDB, Redis, Reverb keys).
- Installed Fortify, Livewire, Reverb, Larastan.
- Tooling: `phpstan.neon` (level 5), pre-commit hook, composer scripts (`format`/`analyse`/`check`).
- Design system: CSS tokens, dark mode, global no-animation rule.

Decisions and bugs along the way:
- Larastan is wired via a direct `includes: vendor/larastan/larastan/extension.neon` in `phpstan.neon` rather than `phpstan/extension-installer`, to avoid adding another Composer plugin to `allow-plugins`.
- Design tokens in `resources/css/app.css` use Tailwind v4's class-based dark mode (`@custom-variant dark (&:where(.dark, .dark *))`). The base `@theme` values are the *light* theme; `.dark` overrides them with the muted palette that is this app's actual default appearance (legacy's default, unmarked theme).
- Did **not** install the standalone `alpinejs` npm package (removed after installing it) — Livewire v4 bundles its own Alpine.js instance and injects it via `@livewireScripts`; adding a second copy causes a documented "multiple instances of Alpine" runtime error. Any `x-data` interactivity relies on Livewire's bundled Alpine.
- End-to-end verification via the actual `docker compose` stack (not just `php artisan test` on the host) surfaced three real infrastructure bugs, all fixed in `docker/php/Dockerfile`/`docker-compose.yml`:
  1. `pecl install redis` was failing (`phpize`/`autoconf` not found) because the preceding `docker-php-ext-install` step installs its own build toolchain and removes it again within that same `RUN` layer. Fixed by wrapping it in its own `apk add --virtual .build-deps ${PHPIZE_DEPS} && ... && apk del .build-deps`.
  2. `app`, `queue`, and `reverb` each declared their own **anonymous** `/var/www/html/vendor` volume — anonymous volumes are per-service, not shared, so `composer install` inside `app` never reached the other two, which crash-looped on a missing `vendor/autoload.php`. Fixed by switching to named, shared volumes (`vendor_data`, `node_modules_data`).
  3. Compiled Blade/Livewire view caches under `storage/framework/views/` record the **absolute source path** for staleness checks (`filemtime()`), and that directory was bind-mounted — shared byte-for-byte between host and container. Running tests on the host then hitting routes through docker (or vice versa) produced `filemtime(): stat failed` errors and pages silently rendering as the default `welcome` view. Fixed with its own named volume (`storage_views_data`), seeded as the `nobody` user (php-fpm's configured user) via `mkdir -p storage/framework/views && chown -R nobody:nobody storage/framework/views` in the Dockerfile.
  4. Separately: after `docker compose up -d` recreates a service (e.g. `app`) without also recreating `nginx`, nginx keeps proxying to the old container's now-stale IP and returns 502 until `docker compose restart nginx` (`fastcgi_pass` resolves the hostname once, not per-request). Not a bug, just an operational step to remember.
- Bumped `phpunit.xml`'s `memory_limit` to 512M — Boggle's `Solver` (see the Boggle section below) builds an ~80k-word dictionary per test process, and a whole test file resolving it repeatedly (Laravel's `TestCase` boots a fresh app per test) could exceed the 128M CLI default and fail with an unhelpful empty/truncated test run.
- **Laravel Cloud build failure: `npm ci` missing a platform-specific lock file entry.** Adding `playwright` as a devDependency (for the Pest browser-testing setup, see below) triggered `npm install`, which rewrote parts of `package-lock.json` — and exposed a pre-existing gap in it: `@napi-rs/wasm-runtime` (a transitive optional dependency of Vite 8's Rolldown bundler) declares a peer dependency on `@emnapi/runtime@^2.0.0-alpha.3`, but the lock file only had a separate, non-satisfying `1.11.1` copy resolved elsewhere in the tree for a different platform variant. This didn't surface in local `npm ci` runs on macOS/arm64 (the platform the lock file was generated on) — only in Laravel Cloud's Linux build container, which needed the platform-specific resolution the existing lock file never captured. Fixed by deleting `package-lock.json` entirely and letting `npm install` regenerate it from `package.json` (unchanged) in one pass, which correctly recomputes the full cross-platform optional-dependency graph rather than incrementally patching it. Verified with a genuine clean-room `npm ci` (no `node_modules` present) and `npm run build` succeeding locally before committing — a `--dry-run` or a `npm ci` with `node_modules` already present will not reliably catch this class of bug, since it doesn't force full re-resolution the way a truly clean install does.

## Authentication & passkeys

- Fortify + passkeys config, custom auth views (no Breeze templates).
- Profile extension migration (`username`, `is_public`) + profile view.

Decisions and bugs along the way:
- `laravel/passkeys` is not a separate install step — Fortify v1.37 (resolved by `composer require laravel/fortify`) depends on it directly and ships native passkey support via `Features::passkeys()` in `config/fortify.php`, including `PasskeyAuthenticatable`/`PasskeyUser` contracts. No standalone `passkeys:install` command exists.
- The `@laravel/passkeys` **npm** package (`resources/js/app.js`) is still needed separately — that's the browser-side WebAuthn ceremony helper, unrelated to the server-side package above.
- Ran `fortify:install`; enabled `registration`/`resetPasswords`/`emailVerification`/`updateProfileInformation`/`updatePasswords`/`passkeys` in `config/fortify.php` (`twoFactorAuthentication` left disabled — not in scope, see `docs/TODO.md`). `User` implements `MustVerifyEmail` + Fortify's `PasskeyUser`/`PasskeyAuthenticatable`. No standalone `config/passkeys.php` — Fortify owns passkey config directly under `fortify.passkeys` (`relying_party_id`/`allowed_origins`/`timeout`), derived from `APP_URL`. Built `resources/views/layouts/app.blade.php` (theme-init script + footer toggle) and `resources/views/auth/{login,register,forgot-password,reset-password,verify-email,confirm-password}.blade.php`, wired via `Fortify::viewPrefix('auth.')`. Passkey WebAuthn ceremonies (login, confirm) are wired via `@laravel/passkeys`' vanilla JS API in `resources/js/app.js`, triggered by `[data-passkey-login]`/`[data-passkey-confirm]` buttons — passkey *registration* (`/user/passkeys`) requires an authenticated user, so that UI lives on the profile page, not the login/register screens. Added a placeholder `/home` route+view as the post-login destination until the real dashboard existed. Added `tests/Feature/Auth/{RegistrationTest,AuthenticationTest}.php`.
- Added `username`/`is_public` columns (migration `add_profile_fields_to_users_table`), added both to `User`'s `#[Fillable]` list and cast `is_public` to `boolean`. Built the profile editor as a Livewire v4 full-page single-file component at `resources/views/pages/⚡profile.blade.php`, routed via `Route::livewire('/profile', 'pages::profile')` (the ⚡ prefix and `pages::` namespace are Livewire v4 defaults). It lists/deletes the user's passkeys (via `$user->passkeys()`) and exposes an "Add a Passkey" button wired to the same `@laravel/passkeys` client used on the auth pages. Found and fixed a real bug: `UserFactory` didn't set `is_public` explicitly, so a freshly-created-but-not-reloaded `User` instance had `is_public === null` in memory (a DB-side default Eloquent doesn't pull back after insert), throwing a `TypeError` when assigned to the component's `bool $is_public` property. Fixed by setting `is_public => true` explicitly in the factory. Added `tests/Feature/ProfileTest.php`.

**Passkey login "remember me", the password-confirmation dead end, and native browser dialogs throughout passkey management.** Three related reports: passkey logins never persisted past the normal 2-hour session lifetime (password-login sessions already had a working "Remember me" checkbox — Fortify's `AttemptToAuthenticate` already wires `$request->boolean('remember')`, nothing to fix there); adding a passkey from `/profile` just showed an alert reading "Password confirmation required." and went nowhere; and naming/removing a passkey used `window.prompt()`/`wire:confirm`'s native `confirm()`, both OS-chrome dialogs this app's low-stim design avoids everywhere else.
- **Passkey remember-me**: `@laravel/passkeys`' JS client (`node_modules/@laravel/passkeys/dist/passkeys-yRK3MD0m.js`) hardcodes its login request body to `{ credential }` — there's no way to send a `remember` field through its public API, so the backend's `PasskeyVerificationRequest::remember()` (`$this->boolean('remember', false)`) could never see anything but its `false` default. Fixed by binding `Laravel\Passkeys\Http\Requests\PasskeyVerificationRequest::class` to a new `App\Http\Requests\RememberedPasskeyVerificationRequest` (in `AppServiceProvider::register()`) that overrides `remember()` to always return `true` — passkeys are already phishing-resistant public-key credentials, so treating every passkey login as "remembered" was the simplest correct default. The same request class also backs the *password-confirmation* passkey ceremony (`PasskeyConfirmationController`), but that controller never calls `remember()`, so the override is a no-op there.
- **Inline password-confirmation modal, replacing a dead-end redirect**: `config/fortify.php`'s `Features::passkeys(['confirmPassword' => true])` gates `/user/passkeys/options`/`/user/passkeys`/`/user/passkeys/{id}` behind Laravel's `password.confirm` middleware. `Passkeys.register()` calls those via `fetch()` with `Accept: application/json`, so a stale/missing confirmation trips `RequirePassword`'s JSON branch (423, `{"message": "Password confirmation required."}`) instead of its redirect branch — meaning `session('url.intended')` never gets set. The original `[data-passkey-register]` handler just alert()'d that raw message and stopped. Rather than bouncing the user to the standalone `/user/confirm-password` page (which would've needed a second, separate click to resume the passkey ceremony after redirecting back — losing the click that WebAuthn requires), `resources/views/pages/⚡profile.blade.php` now has an in-page `<dialog>` that confirms via `fetch()` and, on success, immediately retries the original action within the same call chain — same trick as the "Confirm with a passkey" flow already used, chained: WebAuthn's `navigator.credentials.create()` needs a live user gesture, and a quick same-task `await fetch()` doesn't break the browser's "sticky" activation the way a full page navigation does, so confirming and continuing feels like one action instead of two. `config/fortify.php` still gained `redirects.password-confirmation => '/profile'` as a non-JS fallback for the standalone confirm page.
- **Root cause of a much bigger, pre-existing bug found while wiring the modal**: wrong-password submissions silently appeared to *succeed*. Traced to `bootstrap/app.php`'s `shouldRenderJsonWhen(fn ($request) => $request->is('api/*'))` — copied from Laravel's docs example for API-only apps, but this app has zero `api/*` routes. It meant every `ValidationException` thrown outside `api/*` (wrong password on `/user/confirm-password`, and — previously unnoticed — wrong credentials on `/login` too) rendered as an HTML `back()->withErrors()` redirect regardless of the request's `Accept` header, instead of Laravel's own default (`$request->expectsJson()`). `fetch()` follows redirects transparently, so the confirm-password modal's `!response.ok` check saw a followed 200 and treated a wrong password as confirmed. Fixed by removing the override entirely, restoring Laravel's default — verified directly against the route (bypassing the JS) with curl before and after, and confirmed `/login`'s own JSON error path was equally broken beforehand. No prior code in the app depended on the broken behavior (plain `<form>` posts never send `Accept: application/json`, so this never affected non-JS form submissions), so this was a pure latent bug, not a deliberate choice being overridden.
- **Naming, password-confirming, and removing a passkey all use custom `<dialog>`s now** (matching the "Rules" dialog pattern already in `layouts/app.blade.php`), replacing `window.prompt()`, `wire:confirm`, and every `alert()` in the passkey flows (including the sign-in and standalone confirm-password pages' failure alerts, now inline `<p>` errors). Removing a passkey also now requires password confirmation for the first time — `pages::profile`'s old `deletePasskey()` deleted the model directly via Eloquent, bypassing `password.confirm` entirely; it's gone, replaced by a `fetch()` `DELETE` straight to the passkeys package's own `/user/passkeys/{id}` route (with a hand-rolled `X-XSRF-TOKEN` header read from the cookie, the same fallback `@laravel/passkeys` itself uses since there's no `csrf-token` `<meta>` tag in the layout), which already had `password.confirm` wired up and just wasn't being used.
- Added `tests/Feature/Auth/PasskeyTest.php` (remember-me override + its container binding, the confirm-password redirect target, and adding/removing a passkey requiring confirmation, including a cross-user ownership check on delete). Full WebAuthn ceremonies aren't covered by Pest (they need real signed assertion data from a virtual authenticator) — verified manually instead via Claude in Chrome against the local Docker stack: wrong password shows the inline error and stays put; correct password closes the confirm dialog and automatically retries registration in the same gesture (observed reaching the real WebAuthn call, which then fails with "The passkey operation was cancelled." since the automated browser has no platform authenticator — shown inline, not alert()'d); and a seeded passkey's full remove flow (custom confirm dialog → DELETE → list refresh) end to end.

## Room system (shared multiplayer infrastructure)

Built alongside Boggle, reused as-is for Yahtzee's later online-rooms work (see that section) and scoped for Family Feud's own follow-up (`docs/TODO.md`).

- `rooms` table + `App\Enums\RoomStatus` + `Room` model.
- Livewire `GameLobby` component: real-time player list, ready states, host-only config panel, start button.

Decisions and bugs along the way:
- Room system required actually finishing Reverb/broadcasting installation, which infrastructure setup had only partly done (package installed, nothing configured). `php artisan install:broadcasting --reverb` crashed mid-command in this sandbox (no TTY for its npm step), leaving `config/broadcasting.php` + `routes/channels.php` published but no `REVERB_*` env vars and no `laravel-echo`/`pusher-js` npm packages — critically, that half-applied state meant `routes/channels.php` unconditionally crashed **every** artisan command (`Broadcast::channel()` eagerly resolves the `reverb` broadcaster, which throws if the Reverb env vars are null). Fixed by hand: added `REVERB_APP_ID`/`KEY`/`SECRET` + `REVERB_HOST=reverb`/`PORT=8080`/`SCHEME=http` (server-side, internal docker network) and mirrored `VITE_REVERB_*` (client-side, `VITE_REVERB_HOST=localhost`) to `.env`/`.env.example`; ran `npm install laravel-echo pusher-js` manually; ran `php artisan reverb:install` after. **If a fresh clone ever needs this re-run, expect the same TTY crash in non-interactive/CI shells — use the manual env-var + npm-install fallback instead of re-running `install:broadcasting`.**
- Room codes are generated in a `static::creating()` hook using a hand-written random-character-picker (**not** `Str::random()`, which has no charset parameter despite looking like it might) over an alphabet that excludes `0/O/1/I` since codes are read aloud/typed on phones. `Room::notExpired()` local scope. Chose **not** to add a `room_participants` table — "who's currently in the room" is inherently presence-channel membership (ephemeral, tracked by Echo/Reverb), and pre-game "ready" state is similarly transient, so both live only in `GameLobby`'s server-side state, reconstructed from broadcast events, not a DB table (this assumption was later revisited for reconnect-across-the-lobby, see Yahtzee's online-rooms section below — the DB table added there, `RoomSeat`, is scoped to *seat assignment*, not to re-introducing a general "who's in the room" table).
- `App\Events\RoomPlayerReadyToggled` and `RoomGameStarting` broadcast on a `PresenceChannel("room.{code}")`; `routes/channels.php` authorizes by checking the room exists and isn't expired, returning `{id, name, is_host}` (the presence-channel member payload).
- `GameLobby` (`resources/views/components/⚡game-lobby.blade.php`) is a plain **embeddable** Livewire SFC (not a full-page/`pages::` component) since it's meant to be dropped into each game's own room page. Listens for presence events via `getListeners()` returning `echo-presence:room.{code},{here,joining,leaving,RoomPlayerReadyToggled,RoomGameStarting}` — Livewire wires these to Echo automatically as long as `window.Echo` exists (`resources/js/echo.js`).
- Found and fixed a real bug while writing `GameLobbyTest`: the "Start game" button's `@disabled(! $this->allReady)` was cosmetic HTML only — the server-side `startGame()` action didn't actually check `allReady` before flipping the room to `Active` and broadcasting `RoomGameStarting`, so a host could start an unready game by calling the action directly. Fixed by adding `abort_unless($this->allReady, 403)` alongside the existing host check.
- Test-writing gotcha: `Event::fake()` also fakes **Eloquent model lifecycle events**, so any test calling `Event::fake()` before `Model::factory()->create()` on a model with a `static::creating()` hook (like `Room`'s code generator) will silently skip that hook and hit NOT NULL constraint errors. Fix: create fixtures first, `Event::fake()` only around the action under test.
- **Guests can join an online room without an account; hosting one still requires a real account.** Laravel's private/presence channel authorization always authenticates via the guard with no "let anyone in" option — there is no way to admit a truly anonymous visitor to a Reverb presence channel. Solved with a throwaway account: `User::createGuest(?string $name)` creates a real `users` row (`is_guest = true`, a `guest-{uuid}@guests.invalid` email nobody can log back into, a random unusable password, `email_verified_at` pre-filled) and logs it in on the spot — both from the lobby's `joinRoom()` and from the room page's `mount()` (for a bare shared room URL). `is_guest` is the actual gate: `createRoom()` `abort_unless(Auth::check() && ! Auth::user()->is_guest, 403)` server-side. `routes/web.php`'s room route dropped its blanket `auth` middleware entirely in favor of this per-visitor provisioning. `routes/channels.php`'s presence-channel closure needed no changes — once a guest is a real (if synthetic) authenticated user, it's indistinguishable from a registered one. **Accepted trade-off:** guest accounts are never cleaned up automatically — see `docs/TODO.md`.
- **Ready state, reconnect, and the "reconnecting resets you to not-ready" bug**: `RoomPlayerReadyToggled` only ever reaches whoever's actively connected to the presence channel at the instant it fires — a reconnecting client's `onHere()`/`onJoining()` has no way to recover another member's current ready status from the presence payload alone (it only ever carries `id`/`name`/`is_host`, see `routes/channels.php`), so before this fix, everyone re-appeared "not ready" to a client that had just reconnected, even players who'd never actually un-readied. Fixed by persisting each toggle to `Cache::put("room:{code}:ready:{userId}", $ready, now()->addHours(3))` in `toggleReady()`, and reading it back (`Cache::get(..., false)`) in both `onHere()`/`onJoining()` instead of hardcoding `'ready' => false`. `startGame()` now clears every present player's cached flag once consumed — otherwise a replayed room ("Back to room" after a finished game) would have every returning player's `onHere()`/`onJoining()` immediately read back "ready" from the *previous* round, enabling Start Game again before anyone actually re-confirmed for the new one.
- **Seat-carrying payload for game-specific start logic**: `startGame()` now passes its own `$this->players` array along with the existing local `room-game-starting` dispatch (`dispatch('room-game-starting', players: $this->players)`) — Livewire binds dispatched payload args to listener params *by name*, so Boggle's own `onRoomStarting(BoardGenerator $boardGenerator)`, which never declares a `$players` param, keeps working completely unmodified. Yahtzee's own room page is what actually consumes it (see below).

## Boggle

- `App\Services\Boggle\{BoardGenerator,Solver,Scorer}` — Livewire solo play, online multiplayer (`/boggle/room/{code}`), async challenge links (`/boggle/share/{gameSession}`).
- 32 tests across solo, rooms, and challenges.

Decisions and bugs along the way:
- Ported `legacy/boggle-shared.js` to the three service classes and copied `legacy/words.txt` to `storage/app/words.txt` (78,833 words, committed to git — it's not build output, the app reads it directly).
- `BoardGenerator::generate(int $size, ?int $seed = null)` uses `Random\Randomizer` + `Random\Engine\Mt19937` (PHP 8.2+) instead of global `mt_rand`/`Str::random()` state, so the **same seed always produces the same board** — added because online rooms (shared board) and async challenges (replay the same board later) both need this.
- `Solver` does **not** use a nested char-by-char trie — that structure hit ~86MB for the ~79k-word dictionary, uncomfortably close to PHP's 128MB CLI default, and combined with Xdebug's per-array overhead reliably crashed the test process with no output at all. Replaced with two **flat** hashmaps (`words`, `prefixes`, for DFS pruning) — same algorithm, ~31.5MB, faster to build, simpler code. Bound as a container **singleton** so the dictionary is parsed once per worker, not once per request. **Debugging gotcha:** running the full test suite with the old trie under this machine's default PHP CLI (Xdebug enabled by default via Homebrew) produced zero output and a nonzero exit code — no exception, nothing, because Xdebug's memory overhead exceeded the CLI's `memory_limit` so severely that even Collision's error handler couldn't allocate enough to report it. `XDEBUG_MODE=off` surfaces the real error cleanly; the flat-hashmap rewrite fixes the underlying problem either way. If a future test run mysteriously produces empty output with no error, suspect Xdebug + memory_limit before anything else.
- Livewire: `pages::boggle.lobby` (hosts the `boggle-setup` embeddable component), `pages::boggle.play` (tap-to-select word entry via `wire:click` per die plus Submit/Clear, later replaced with a drag gesture — see "Site-wide design system & chrome" below), `boggle-reveal` (post-game word list). Timer uses `wire:poll.1s` against a server-side `endsAt` unix timestamp (only when timed and not yet ended) rather than a client Alpine interval, to avoid clock drift and keep game-end authoritative on the server.
- Ending a game (timeout or manual) always records a `GameSession` + one `GameParticipant`, for both logged-in users (`user_id`) and guests (`guest_name: 'Guest'`).
- **Boggle online multiplayer**, on top of the Room/GameLobby infrastructure:
  - `pages::boggle.room` (route `/boggle/room/{code}`) hosts a host-only board-size/time-limit picker plus the nested `<livewire:game-lobby>`. `onRoomStarting()` (host path) generates the board, creates a `GameSession` (`mode: Online`), attaches it to the room, redirects the host into `pages::boggle.play`. `onRoomStarted()` (every player, via the broadcast) does the equivalent redirect once `game_session_id` is populated.
  - `pages::boggle.play` gained `#[Url] public ?string $room` — when present, `size`/`minutes`/`seed` are **overridden** from the room's `GameSession.settings` rather than trusted from the query string (a player shouldn't change their own board by hand-editing the URL); `endGame()` joins the existing `GameSession`; each `GameParticipant`'s `result` is computed by re-ranking all participants recorded so far against the top score every time someone finishes — deliberately simple/self-correcting rather than trying to detect "everyone's done" and finalize once.
  - Requires an account for **all** participants, not just the host — Reverb presence channels authenticate via the app's default guard before the channel callback even runs, so there's no way to admit an unauthenticated user to `room.{code}` at all. Solo play stays guest-friendly; online rooms don't (closed by the guest-account fix documented under "Room system" above, which covers *joining*, not hosting).
- **Boggle async challenge links**, built on the same "join an existing `GameSession`, rank once more than one participant has finished" logic as multiplayer: `pages::boggle.play` generalizes `isSharedSession` to cover `$room` **or** `#[Url] public ?int $challenge`, rather than duplicating logic. `GET /boggle/share/{gameSession}` is a plain redirect to `pages::boggle.play?...&challenge={id}`, not its own Livewire page. A plain solo game now also stores its `GameSession`'s id onto `$this->gameSessionId` once `endGame()` runs, so the reveal screen can build a `route('boggle.share', ...)` link. The "Copy" button uses a **delegated** `document.addEventListener('click', ...)` matching `[data-copy]`, since it only exists after a Livewire re-render (ending the game) rather than at initial page load.
- **Layout centering bugs (two, same root cause)**: a plain (non-flex) wrapper `<div>` doesn't auto-center a narrower child, even with `items-center` on the child itself. Fixed `pages::boggle.play`'s root element (`class="flex flex-col items-center w-full"`) and the room-code input (was `flex: 1`, stretched to fill the row and centering only the *text* within an oversized box; changed to a fixed width so input+Copy button sit together as one centered unit).
- **Shared-session (room or async challenge) reveal shows who found what, and scores only exclusive discoveries.** Previously every shared game showed the same single-player reveal, and scoring was raw per-word points with no way to know until reveal whether another participant found the same word too. `GameParticipant.stats['found_words']` now persists each participant's full word→points map (previously only the *count*), and `finalizeSharedSession()` recomputes every finished participant's score as the sum of only words *no one else in the session also found*, self-correcting on every finish. The reveal list colors each word by who found it: mine-only (`--accent`), shared by 2+ (`--bar`, "Both/All"), or one of up to four other individual participants (`--rival-1`..`--rival-4`, wrapping via `% 4` for a 5th+). Verified visually via a headless-browser render against the real board/dictionary, not just test assertions. Later extracted into its own `App\Services\Boggle\SharedSessionFinalizer` service class (see the commit-by-commit `docs/CHANGELOG.md` for that specific refactor).
- **Per-game Boggle stats on the profile**, scoped deliberately to Boggle only (the deep-dive metrics — longest word, per-length breakdown, % of board found — are word-game-specific; Yahtzee/Family Feud only get `PlayerStatsService`'s generic per-type summary on the dashboard, though see Yahtzee's own stats page below):
  - `GameParticipant.stats` (already a flexible JSON column, no migration needed) gained a `total_valid_words` key, written in `pages/boggle/⚡play.blade.php`'s `finishGame()` right next to `found_words` — it's just `count($this->allValidWords)`, already computed there via the Solver to render the reveal screen, so persisting it is free; without it, "% of the board found" can't be computed later without re-running the ~80k-word Solver per historical game per view. Reloading the page right after a shared game ended therefore silently started a brand-new, fully replayable attempt (fresh timer, empty board state), and finishing *that* called `GameParticipant::create()` again, producing a second row for the same session/user. Confirmed against the app's own real dev database, not hypothetically: `game_session_id=9` had exactly this — two players, four rows, two of them (`0` words found, immediately superseded) clearly the stale pre-refresh attempt. Regression-covered by three new tests in `tests/Feature/Games/BoggleChallengeTest.php` (remount restores `ended` instead of allowing a replay; finishing twice for the same account updates one row rather than duplicating; guests are unaffected).

## Yahtzee

- `App\Services\Yahtzee\{DiceRoller,Scorer,GameEngine}` + Livewire, pass-and-play only at first (online mode added later — see "Online rooms for Yahtzee" below).

Decisions and bugs, deliberate deviations from the original plan's literal wording:
- `App\Services\Yahtzee\{DiceRoller,Scorer,GameEngine}` split by responsibility: `DiceRoller` is `initial()`/`reroll()` (server-side `random_int`); `Scorer` is the pure per-category calculator (mirrors legacy's `calcScore()`, told `$jokerBonusEligible` rather than working it out itself); `GameEngine` orchestrates the Joker rule / Yahtzee bonus chip (which need a player's other scores) and owns the aggregate math. New `App\Enums\YahtzeeCategory` (13 cases) replaces legacy's plain-object category arrays.
- Livewire: single full-page `pages::yahtzee.play`, mirroring legacy's single-page setup-then-game-then-reveal structure.
- Real bug caught before shipping: `GameEngine`'s helper methods and per-cell `categoryScore()`/`isPickable()` calls are invoked *directly from the Blade template*, not via `wire:click`. Livewire's automatic method-dependency-injection only applies to the latter — a plain method call from a render has no framework layer to inject anything, so an initial version with `GameEngine $engine` as a method parameter would have fatal-errored the moment the scorecard rendered. Fixed by resolving `GameEngine` once via a `boot(GameEngine $engine)` hook into a private property instead.

**Yahtzee undo + "which player/team is you" attribution.** Reported bug: a logged-in Yahtzee game never showed up in "recent games." By design, not a bug — Yahtzee/Family Feud were single-device pass-and-play games where every local player/team was just a typed name (`guest_name`), never `user_id`, since there was normally no way to know which local player was the account holder (Boggle always has a real, if throwaway, account per player, which is why only Boggle ever showed up). This pass shipped two small, independent pieces:
- **Yahtzee undo**: reinstated legacy's snapshot/restore undo (`pushHistory()`/`undo()`), deliberately dropped when Yahtzee was first ported. A public `array $history` property (must be public — Livewire only persists public properties across requests) snapshots `dice`/`kept`/`rollsLeft`/`players`/`currentPlayer` right before every `roll()` and `scoreCategory()`, mirroring exactly which two actions legacy's `pushHistory()` guarded. Not usable once `$gameOver` — `endGame()` already persists a `GameSession`/`GameParticipant` the moment the last category is scored, and unwinding that DB write was out of scope. Redo was never surfaced in legacy's own UI either and stays out here too.
- **"Which player/team is you?"**: an optional setup-time picker (`meIndex` for Yahtzee), shown only `@auth`, using the existing `.option`/`.option-group` button-group markup verbatim. Whichever local player is picked gets `user_id`/`guest_name` swapped the same way Boggle's own solo games already do — every other participant in that game stays guest-only, avoiding the double-counting trap of tagging *every* local player as "you" (which would skew win-rate/avg-score for any multi-player local game). No migration needed and no changes needed to `PlayerStatsService` — it already queries by `user_id`.

**Yahtzee sizing: the full scorecard now fits one screen on desktop without scrolling.** Reported as a TODO ("Yahtzee should all fit on one screen on desktop"); the page already had CSS aimed squarely at this (`body.scrollable.yahtzee-play.in-game { height: 100dvh; }`, `#yahtzee-game`'s flex/`min-height:0` chain, `.card-wrap`'s `overflow: auto` safety net) but none of it actually worked. Two real, independent bugs, found by measuring layout via a scripted headless-Chrome (CDP) session rather than eyeballing screenshots:
- **The `in-game` class never reached the live `<body>`, ever, even on first load.** `<x-slot:bodyClass>yahtzee-play{{ $started ? ' in-game' : '' }}</x-slot>` is a layout-level slot, evaluated exactly once at the page's first render — and `$started` is always `false` at that moment (the setup screen is what mounts first), so `in-game` was never in the server-rendered HTML to begin with. Worse, `startGame()`'s own Livewire round trip only re-renders and morphs the component's *own* root element, never touching `<body>` in the surrounding layout — the same bug class documented for the button-bar's `@teleport` fix (see "Site-wide design system & chrome" below), and already fixed once before for Boggle's own `in-game` toggle. Yahtzee just hadn't gotten that same treatment. Fixed identically: an `@script` block calling `document.body.classList.toggle('in-game', $wire.started)` plus a `$wire.$watch('started', ...)` for every later Livewire update; removed the now-provably-dead `$started ? ' in-game' : ''` from the bodyClass slot entirely rather than leaving inert markup.
- **The root `<div>` wrapping the whole component broke the flex chain from `<body>` down to `#yahtzee-game`.** `#yahtzee-game { flex: 1; min-height: 0; }` only means something if its *parent* is a flex container sized by the page — but that parent was a bare `<div>` with no flex classes at all, so it just sized to its content's natural height (auto), and `#yahtzee-game`'s own `flex: 1` had nothing to grow or shrink against. Same underlying lesson as Boggle's own centering bugs (a plain wrapper `<div>` doesn't participate in a flex layout it isn't itself part of). Fixed by giving that root `<div>` `class="flex flex-col items-center w-full flex-1 min-h-0"`, matching the pattern Boggle's own play page root already uses.
- With both of those actually wired up, `<body>` correctly clipped to `100dvh` — but `.card-wrap` (holding the 17-row table) still needed its own internal scrollbar, because cell font-size/padding were sized off raw viewport `vh`, entirely disconnected from how much vertical room the dice area above it actually used, or from the fixed row count. Fixed by giving `.card-wrap` `container-type: size` and switching `table.scorecard th`/`td`'s font-size/padding to `cqh` (a percentage of `.card-wrap`'s own resolved height) instead of `vh` — the 17 rows now always divide up whatever space is actually left, self-adjusting to any dice-area height or viewport size without referencing the row count or viewport height directly.
- Verified across 2 and 8 players (min/max) at four viewport heights (720/768/900/1080, 1440/1366/1280/1920 wide) via the same scripted CDP session: `document.body.scrollHeight` exactly equals `window.innerHeight` and `.card-wrap`'s `scrollHeight` exactly equals its `clientHeight` in every case — zero pixels of overflow. No test coverage exists (or was added) for pure CSS layout fit, which isn't something Pest can assert on — this class of bug is exactly what the new Pest browser-testing setup (see the bottom of this file, and `CLAUDE.md`) is meant to start catching automatically going forward.

**Online rooms for Yahtzee** (the multi-session item scoped out in `docs/TODO.md`; Family Feud's own follow-up is what remains there now). Reused `Room`/`RoomStatus`/`routes/channels.php`/`⚡game-lobby.blade.php`/`RoomGameStarting` entirely as-is — all genuinely game-agnostic already (see "Room system" above) — and added the shared infrastructure this app didn't have yet:
- **`GameSession.state`** (new nullable `json` column): the persisted, server-authoritative blob for an in-progress online game (`seats`, `currentSeat`, `dice`, `kept`, `rollsLeft`, `gameOver`) — broadcast via a new, deliberately game-agnostic `App\Events\RoomGameStateUpdated` (`ShouldBroadcastNow`, full state each time rather than a delta, matching this app's preference for simplicity over premature optimization) any time a seat successfully rolls/keeps/scores.
- **`RoomSeat`** (new model/table/factory): `room_id` + `seat_index` + `user_id`, unique on both pairs — what lets a reloading phone recover "you are seat 2" from `Auth::id()` alone, independent of ephemeral presence-channel membership. Deliberately minimal (no `team_index`/`is_captain`) since Yahtzee has no teams; Family Feud's own follow-up adds those when it actually needs them.
- New `pages::yahtzee.room` (mirroring `pages::boggle.room`), consuming `game-lobby`'s `$players` payload (see "Room system" above) to seat-assign every ready player at start time, in join order.
- **Turn authorization**: `roll()`/`toggleKeep()`/`scoreCategory()` on `pages::yahtzee.play` each gained `abort_unless($this->room === null || $this->mySeatIndex === $this->currentPlayer, 403)` — local pass-and-play (`$room === null`) completely untouched by this. `mySeatIndex` (null for a spectator/host connection) is looked up from `RoomSeat` at `mount()`, not guessed. **Bug found and fixed**: `isPickable()` initially only checked `$playerIndex === $this->currentPlayer` — i.e. whose *column* this is, not who's actually looking at it. Any other connected seat viewing the current player's column got a live, clickable `wire:click="scoreCategory(...)"` wired onto that cell, which then 403'd server-side the moment they actually tapped it, instead of simply never being clickable in the first place. Fixed by adding `&& $this->isMyTurn` to `isPickable()`'s conditions.
- **Broadcast payload binding gotcha**: local Livewire dispatches (`$this->dispatch(...)`) bind named args to listener parameters by name, but Echo/broadcast custom events deliver their entire `broadcastWith()` payload as **one positional argument** — an initial `onStateUpdated(...)` written to expect named args silently failed to update anything. Fixed to match the existing `onReadyToggled(array $event)` pattern already used elsewhere in this codebase: `onStateUpdated(array $event)` reads `$event['state']` itself.
- **Undo intentionally isn't supported online** (hidden in Blade, `undo()` early-returns when `$room !== null`) — rewinding shared state other seats may have already seen broadcast is a real, unsolved design problem (whose view wins?) with no user request driving it, so it was cut rather than half-solved.
- **Reconnect / mid-game recovery**: `mount()`, when `$room !== null`, resolves the `Room`, loads its `GameSession`, and hydrates `$players`/`$dice`/`$kept`/`$rollsLeft`/`$currentPlayer`/`$gameOver`/`$started = true` straight from `GameSession->state` — a reload recovers mid-game state instead of re-running local setup screen from scratch. Combined with the lobby's own ready-state persistence fix (see "Room system" above), a phone that loses connection at any point — pre-game or mid-game — can reload and land back exactly where it was.
- **Spectator/host view, and "watch only" for a seated player on a second device**: whenever a connected account occupies no seat in the room (`mySeatIndex === null`), or a seated player explicitly opts into a `#[Url] public bool $spectate` flag (a per-device URL toggle, not account-wide — deliberately so switching it on a casting device doesn't also switch it on the device the same account is actually playing from), the view becomes read-only: dice values and kept/selected highlighting are still shown live (a spectator benefits from watching the roll), but clicking a die to keep it and the Roll button itself are hidden outright rather than merely disabled — a disabled-but-visible Roll button invites clicking it anyway, the exact class of bug `isPickable()` just got fixed for above. A "Player view"/"Watch only" toggle button (teleported into `#game-actions`, shown only to a seated player) flips `$spectate` for the local device only.
- **Mobile scoreboard drawer**: a "Scores" button (`id="scores-btn"`, teleported into `#game-actions`, online games only, desktop-hidden via CSS since every column already fits on the main desktop scorecard) opens a full-screen `<dialog class="scoreboard-dialog">` showing the same scorecard read-only for every player, reusing a newly-extracted `<x-yahtzee-scorecard-table>` Blade component — so a group playing purely on their own phones, with no separate host/TV device, can still check the shared board on demand. That extraction is a plain Blade component (not a `@include`, which this codebase had never used and turned out not to propagate `$this` into the included view the way the surrounding Livewire single-file component does) — `$livewire` is passed in explicitly as a prop instead, sidestepping the ambiguity entirely.
  - **`dialog:not([open]) { display: none }` UA-default bug**: the drawer's own `dialog.scoreboard-dialog { display: flex; ...; inset: 0; }` rule set `display` unconditionally, which — since author styles always beat the browser's built-in UA stylesheet regardless of specificity — silently overrode the browser default that hides a `<dialog>` without the `open` attribute. The *closed* dialog was therefore a permanent, invisible-but-present full-viewport `position: absolute; inset: 0` overlay for every single visitor, on every page load, intercepting layout (and, given a stray click, input) the entire time. Confirmed live via `getComputedStyle`/`hasAttribute('open')`. Fixed by scoping the whole ruleset to `dialog.scoreboard-dialog[open]` — `.rules-dialog` never had this bug only because it happens to not set `display` at all, leaving the UA default intact.
  - **Closing on unrelated re-renders**: the native `open` attribute is untracked DOM state; any Livewire re-render (triggered by *any* broadcast, including from other players' actions) morphs the tree back to server-rendered markup (which never has `open` on it), silently closing the drawer out from under whoever had it open, mid-read. Fixed with `wire:ignore.self` on the `<dialog>` — `.self`, not a bare `wire:ignore`, so the scorecard *inside* still updates live while the drawer's open; only the dialog element's own open/closed attribute is left untouched by morphing. Verified live: opened the drawer, simulated an incoming broadcast (`wire.call('onStateUpdated', {state: newState})`), confirmed `dialog.hasAttribute('open')` stayed `true` while the displayed score updated underneath, and confirmed the close (×) button still worked afterward.
  - **Equal-width columns, both mobile and desktop**: per-cell `width`/`max-width` turned out not to be reliably binding under `table-layout: auto` (two columns both declared `width: 10ch` still rendered at visibly different widths) — fixed with a `<colgroup>`/`<col>` per column instead, which *is* binding, but only once `table-layout: fixed` is set **and** the table's own `width` is an explicit, definite value rather than `auto` (confirmed live: `fixed` plus an auto table width still let a longer name's column render wider than a shorter one's). The definite width is computed from CSS custom properties, `--scorecard-category-width`/`--scorecard-player-width` (`:root`-level, so `<col>`'s widths and the table's own total width can never drift out of sync) times a `--player-count` value set inline per-render by `<x-yahtzee-scorecard-table>`.
  - **Mobile single-seat narrowing broke desktop, then broke itself**: on mobile, a seated player's own phone hides every other seat's column (`not-mine`, driven by `mySeatIndex`) since the drawer above already covers "see everyone." Collapsing just the *cells* (`display: none`) left each hidden column's `<col>` still contributing its share to `--player-count`'s total width, reserving a dead visual gap where they used to be. Collapsing the `<col>` itself (`width: 0`) instead of the cell fixed the gap — but combining `display: none` on the cell **and** `width: 0` on its `<col>` simultaneously turned out to be actively broken in a different way: under `table-layout: fixed`, Chromium then rendered the *next* (still-visible, "mine") column's cells at zero width too, even though that column's own `<col>` correctly still specified its real width — confirmed via precise `getBoundingClientRect()` measurements and a live diagnostic test reverting the cell's `display` back to its default. The actual, final fix was to remove `display: none` from the cells entirely and collapse *only* the `<col>` — the existing `overflow: hidden` on non-category cells already makes a zero-width cell show nothing, with no separate `display` override needed or safe to add.
  - **Desktop category labels truncating**: the `18ch` category-column width, sized against the *mobile* font-size, truncated labels like "Bonus (63+ = 35)"/"Upper Subtotal" once the responsive font-size clamp reached its own max (28px), which only happens once `.card-wrap` has real desktop-height room to grow into — confirmed by forcing `font-size: 28px !important` via an injected style and checking `scrollWidth > clientWidth`. Fixed by widening both `--scorecard-category-width`/`--scorecard-player-width` (18ch/10ch mobile → 22ch/16ch) inside a `@media (min-width: 900px)` override of the `:root` custom properties above.
  - **Row labels cut off on mobile, and not sticky**: the category column was getting squeezed hard enough on a real phone width to visibly cut off labels, competing with the (now fixed-width) player column for room. Fixed by shrinking and un-bolding that column's font specifically on mobile (`font-size: clamp(9px, 3.2cqh, 20px); font-weight: normal;`), and making it `position: sticky; left: 0;` (against `.card-wrap`'s own `overflow: auto` scrolling ancestor) so the row you're looking at stays identifiable while scrolling horizontally through more players than fit on screen at once.
  - **Roll button and dice sharing one row; smaller dice**: `.dice-area` used to `flex-wrap: wrap`, and `.row`'s own width (`min(94vw, 64vh, 1200px)`) claimed nearly the full available width, leaving no room for Roll/Undo beside it — they always landed on their own row below the dice. Switched `.dice-area` to `flex-wrap: nowrap` and meaningfully narrowed `.row` (`min(56vw, 42vh, 720px)`) and its die font-size (`clamp(18px, 5vmin, 72px)`, down from `clamp(26px, 8vmin, 120px)`) so Roll/Undo fit on the same row as the dice — freeing the vertical space a second controls row used to cost for `.card-wrap` to grow into instead, making the scorecard itself taller and each category cell easier to tap precisely.
- **Ending the game**: reuses the existing `endGame()`/participant-creation logic as-is, with one simplification specific to online mode — each seat's `RoomSeat->user_id` is always a real (if possibly guest) account, so `GameParticipant` attribution no longer needs the local mode's `meIndex`-guessing; every seat writes `user_id` directly. No separate `RoomGameEnded` broadcast is needed (unlike Boggle) — Yahtzee's shared turn state means every player already learns "game over" from the same final `RoomGameStateUpdated` (`gameOver: true`) that ended the last turn.

## Family Feud

- Question seeder (32 questions), `JudgeService` (OpenRouter/Claude Haiku), single shared-screen Livewire game (no separate host/display split — see below).

Decisions, deliberate deviations from the original plan's literal wording (ported from `legacy/family-feud.html` / `legacy/netlify/functions/game.js` / `legacy/family-feud-spec.md`):
- **No `FamilyFeudHost`/`FamilyFeudDisplay` split, no Reverb.** The original plan called for two components connected over Reverb, but the legacy spec's core design decision is explicit: *"The game works on one screen only because an LLM is the judge, not a person... there is no hidden information on the screen, so a single shared view is correct. Do not build a separate host and board view."* Built as one Livewire page (`pages::family-feud.play`), same pattern as Yahtzee's pass-and-play. (Family Feud's own online-room follow-up, reusing the seat/state infrastructure Yahtzee proved out above, is the one piece of the original combined scope still deferred — see `docs/TODO.md`.)
- **No queued job.** The plan called for a queued `JudgeFamilyFeudAnswer` job "so the UI doesn't block," but there's no UI to keep unblocked in the first place if it's one synchronous screen — the legacy version's own `fetch()` call is itself a blocking round-trip from the browser's perspective. `wire:loading` on the submit button/input gives the "Checking..." state for free. `JudgeService::judge()` uses a 15s HTTP timeout.
- **Security-critical port hazard, not a deviation:** the legacy security model works by never sending the answer bank to the browser at all (it lives only in the Netlify function). A naive Livewire port would break this much more severely — every Livewire public property gets serialized into the page's `wire:snapshot` HTML on every request, so holding `$this->questions` as full rows would leak every hidden answer to anyone opening dev tools, on every request. Fixed by **never storing `answers` as a public property at all** — `$this->questions` only ever holds the client-safe shape (`FamilyFeudQuestion::toSafeArray()` → `{id, prompt, answerCount}`), and every action that needs real answers re-fetches the question fresh from the database inside that action. Confirmed by a `not->toHaveKey('answers')` test assertion.
- Team names use `guest_name` on `GameParticipant` (never `user_id`) — the same attribution gap Yahtzee had before its own "which player is you" picker (see Yahtzee's section above); Family Feud's own follow-up will need the equivalent for teams/captains.
- Initially kept `wire:confirm` (native browser `confirm()`) for Skip Question/End Game/Reveal confirmations as the simplest option for v1, even though the legacy spec calls out native browser dialogs as an accessibility violation ("bright OS-default modal"). Later replaced with the reusable `<x-confirm-dialog>` component — see "Low-stim confirm dialogs" under "Site-wide design system & chrome" below.
- Test-writing gotcha: `Http::fake()` calls don't replace earlier registrations for the same URL pattern — the *first*-registered stub keeps matching first, so simulating "judge fails, then a retry succeeds" needs `Http::fake(['url' => Http::sequence()->push(...)->push(...)])` in one call, not two separate `Http::fake()` calls.
- Verified `OPENROUTER_API_KEY` with one real (tiny-cost) call through the deployed docker stack via `php artisan tinker` — "sun cream" correctly matched to a "Sunscreen" answer.

**Online rooms for Family Feud** (the last piece of the original combined-with-Yahtzee scope, deferred in `docs/TODO.md` until now). Reused `Room`/`RoomStatus`/`routes/channels.php`/`⚡game-lobby.blade.php`/`RoomGameStarting`/`GameSession.state`/`RoomGameStateUpdated` entirely as-is — the last two events' own docblocks were already written expecting this — and added the parts that are genuinely Feud-specific: teams with multiple players each, a captain-gated steal, and a within-team rotating turn pointer.
- **Team/captain assignment defaults to alternating by join order, but the host gets an explicit assignment screen to override it before the round starts.** Initially shipped fully automatic with no UI at all (even seat index → team 0, odd → team 1, first seat on each team captain, mirroring Yahtzee's "seat index = join order" simplicity) — revised almost immediately after a follow-up request for host control over who's on which team. `pages::family-feud.room` gained a whole intermediate step: `game-lobby`'s "Start Game" click still dispatches the same local `room-game-starting` event, but `onRoomStarting()` no longer creates the `GameSession`/`RoomSeat` rows itself — it only snapshots the ready players into `$readyPlayers` (with the alternating split as the *starting* `$teamAssignments`/`$captainAssignments`) and flips `$assigningTeams = true`, rendering a new screen with a "Move to {other team}" and "Make Captain" button per player. `startRound()` (host-only, gated on `canStartRound` — both teams non-empty) is what now actually builds `teamSeats`/creates the `GameSession`/creates `RoomSeat` rows/broadcasts `RoomGameStarting`/redirects, using whatever the host's own `$teamAssignments`/`$captainAssignments` ended up as rather than the untouched default. `moveToTeam()` always strips the moved player's own captaincy (an explicit "Make Captain" tap is required on their new team, never automatic) and calls `ensureEachTeamHasACaptain()`, which promotes a team's first remaining member if a move just left it captain-less — a non-empty team can never end up with zero captains through the UI. Only the host's own connection ever sees `$assigningTeams = true` — `'room-game-starting'` is a local (non-broadcast) Livewire dispatch that only reaches the request that triggered it, and `game-lobby::startGame()` already aborts for a non-host caller — so every other connected player just keeps looking at the ordinary lobby, unaware anything happened, until `RoomGameStarting` actually broadcasts once the host confirms. `room_seats` gained `team_index` (nullable unsignedInteger) and `is_captain` (boolean, default false) — nullable/defaulted specifically so Yahtzee's own existing `RoomSeat::create()` call, which sets neither, keeps working completely unmodified. **Accepted limitation:** a host who reloads mid-assignment loses their in-progress picks and lands back on the plain lobby (`$assigningTeams`/`$readyPlayers`/etc. are plain Livewire component properties, not persisted anywhere, so a real page reload — as opposed to a normal same-tab Livewire round trip, which persists them fine — remounts fresh) — not worth persisting a draft-state screen to the database for.
- **Turn authority, all newly added — `submitGuess()`/`retryGuess()`/`skipQuestion()`/`swapControl()`/`revealManually()`/`awardManual()`/`nextRound()`/`nextRoundSummary()`/`endGame()` had zero authorization at all before this**, exactly as `docs/TODO.md` flagged for `submitGuess()` specifically. During the `Play` phase, only the controlling team's current turn-pointer seat may guess/skip/swap; during `Steal`, only the *stealing* team's captain may act, regardless of the turn pointer (a captain-only action never advances it). `RoundEnd`/`RoundSummary`/`Manual`/`GameEnd`-phase actions are gated to "any seated player" instead of a specific turn-holder, since those are shared "we're ready to continue" decisions, not guessing turns.
- **The within-team turn pointer** (`teamTurnPointer`, one index per team into that team's own `teamSeats` list) rotates by one, wrapping, every time the controlling team submits a *resolved* guess during `Play` — captured via `judgeGuess()` (the single private method both `submitGuess()` and `retryGuess()` already routed through), which is also where the pointer-advance and `syncOnlineStateIfNeeded()` call both live now. A judge-unreachable failure (`pendingGuess`) does **not** rotate the pointer or sync online state — that failure and its Retry option are deliberately local-device-only state, same reasoning as keeping `guessInput`/`turnOptionsOpen` unsynced.
- **The judge call stays exactly where it was: synchronous, in-request, inside whichever seat's own guess triggered it.** No queue was added — matches both local pass-and-play's existing behavior and the TODO's own explicit instruction. `RoomGameStateUpdated` broadcasts the result once it resolves, same as every other mutating action.
- **`GameParticipant` attribution is one row per seated user, not one row per team** — a real improvement over local mode, not just a port of it. Local pass-and-play still needs `$meTeamIndex`'s guessing trick (there's no way to know which local team is the account holder in general), but online, every seat's `user_id` is known for certain, so every real account that played gets its own correctly attributed row (same reasoning as Yahtzee dropping `meIndex` for its own online mode). Each row also gets a new `stats` payload (`team_index`, `is_captain`, `round_history` — that participant's own team's points per round only) on **both** the local and online `endGame()` branches, added as part of the stats-page work below since it was free to compute right there either way.
- `pages::family-feud.room`'s `onRoomStarting()` silently declines to enter the team-assignment screen at all if the question bank is empty (mirrors `startGame()`'s own local guard against the exact same fresh/unseeded-deployment crash) rather than trying to message an error back through the lobby's own start-game event, which has no return path. A team ending up with zero seated members — the scenario `endGame()`'s per-seat `GameParticipant` loop would otherwise have to handle specially — can no longer actually happen: `canStartRound` (both teams non-empty) blocks `startRound()` entirely, so this is enforced at the assignment screen rather than tolerated at game-end.
- **Host-only room settings** (rounds + two team names) live on the new `pages::family-feud.room` page, mirroring Boggle's room page (host-only board-size/time picker) rather than Yahtzee's (which has nothing to configure pre-start at all).
- Found and fixed one real test-writing bug of our own while writing the browser test suite: an early version of "the acting seat sees the guess form, the other seat sees a waiting message" held two `visit()` pages open in one test, with a content assertion running on the first before the second was ever created — exactly the specific pattern `docs/DEVLOG.md`'s own "Automated browser testing" section already documents as a reliable 30-60s hang in this Playwright setup. Split into two separate one-page-per-test cases (mirroring `YahtzeeRoomBrowserTest`'s existing convention) rather than fighting it.
- Added `tests/Feature/Games/FamilyFeudRoomTest.php` (17 tests: host/join flows, the team-assignment screen's default split/moves/captain-reassignment/`canStartRound` gating, that confirming persists the host's *customized* teams rather than the untouched default, turn-pointer-only and captain-only-during-Steal authorization — including that a non-captain teammate on the stealing team is still forbidden, not just the controlling team — pointer rotation, reload rehydration, per-seat `GameParticipant` attribution) and `tests/Browser/FamilyFeudRoomBrowserTest.php` (7 tests, one real browser page per test with the rest of the room DB-seeded, same convention as `YahtzeeRoomBrowserTest`) — covering exactly the `@teleport`/conditional-visibility bug class this app has repeatedly shipped broken before (see "Site-wide design system & chrome" below), since this pass adds several new conditionally-shown elements (the guess form vs. a waiting message, the Reveal/End Game button-bar buttons hidden from spectators, and now the team-assignment screen's own real-DOM Start Round enabled/disabled state). The two new team-assignment browser tests drive `onRoomStarting()` directly via `window.Livewire` (the same JS-injection pattern `YahtzeeRoomBrowserTest` uses for `onStateUpdated()`) to stand in for `game-lobby`'s own presence-broadcast-dependent "Start Game" dispatch, which this test environment's `BROADCAST_CONNECTION=null` can't otherwise trigger for real.

**Family Feud stats pages**, added alongside the online-rooms work and mirroring `profile.yahtzee`/`YahtzeeStatsService` (Boggle's own deep-dive metrics are word-game-specific and don't apply here). New `App\Services\Stats\FamilyFeudStatsService` reads `team_index`/`is_captain`/`round_history` back out of each `GameParticipant.stats` (see above); `bestMetrics()` surfaces "Highest score" and "Biggest single round" (the latter derived from each game's own `round_history` max, omitted entirely if no game ever scored above zero in a round — same "omit rather than show a misleading zero" rule `YahtzeeStatsService::bestMetrics()` already follows). New `profile.family-feud`/`profile.family-feud.show` routes (registered before the `/profile/{username}` wildcard, same reasoning already given for `/profile/boggle` and `/profile/yahtzee`) and two new Blade pages adapted directly from `pages::profile.yahtzee`'s own two files — the show page adds a "Captain" badge when `stats['is_captain']` is true and a round-by-round breakdown table instead of Yahtzee's per-category scorecard, since Family Feud has no per-category concept. `<x-player-stats>`'s `match ($stat['type'])` gained a `GameType::FamilyFeud => 'profile.family-feud'` arm (and, with all three `GameType` cases now covered, the `default => null` fallback was dropped in favor of an exhaustive match). Added `tests/Unit/Stats/FamilyFeudStatsServiceTest.php` and `tests/Feature/ProfileFamilyFeudTest.php`, mirroring the equivalent Yahtzee test files.

## User profiles & stats

- `/dashboard` (own stats) and `/profile/{username}` (public, `is_public`-gated).

Decisions:
- `App\Services\Stats\PlayerStatsService::forUser()` groups a user's `GameParticipant` rows by their `GameSession`'s `type` (via Eloquent collections, not a raw SQL `join`/`groupBy` — the game-history size for a single hobbyist player is nowhere near "needs a DB aggregate" territory) and computes games played / win rate / average score per type. `recentGames()` needed `->latest()->latest('id')` rather than just `->latest()` — a real bug caught by a test: two participants recorded in the same second (plausible, e.g. a multiplayer room where every player's `endGame()` fires within the same clock second) sort in an undefined order without an `id` tiebreaker.
- **Repurposed `/home` into the real `/dashboard`** rather than keeping both — `/home` was always documented as a placeholder until this phase. Updated `config/fortify.php`'s `'home'` redirect target, the passkey-login JS fallback redirect, and the two auth tests asserting a `/home` redirect. Deleted the placeholder view/route entirely rather than leaving a compatibility redirect, since nothing external linked to it yet.
- **Dropped "friends activity"** from the dashboard (mentioned once in the original plan) — no friends/social-graph table exists anywhere in the schema, so this read as aspirational filler rather than a concretely specified feature. See `docs/TODO.md`.
- **No image avatars** — `<x-avatar>` is a generated initial-letter badge; nothing ever specced an upload/Gravatar integration. See `docs/TODO.md`.
- **"Clear All Stats"** on `/profile` (new "Danger Zone" panel) deletes only the acting user's own `GameParticipant` rows (`$this->user()->gameParticipants()->delete()`), gated behind `<x-confirm-dialog>` (see "Low-stim confirm dialogs" above). Deliberately scoped to the user's own rows, not the `GameSession`s themselves — a shared multiplayer session (e.g. a Family Feud room) stays intact along with every other player's own history on it; clearing never cascades across players. Covered by a Feature test asserting exactly that (another player's row on a session they shared survives) and `tests/Browser/ProfileDangerZoneDialogsTest.php` for the dialog's own open/cancel/confirm behavior.
- **"Delete Account"**, same panel, same dialog component. **Hard delete**, not soft — the schema already anticipated this: `passkeys.user_id`/`room_seats.user_id` cascade-delete, `rooms.host_user_id` cascade-deletes any room the account hosted, but `game_participants.user_id` merely nulls out (nullable FK, `nullOnDelete`), so a shared session's `GameParticipant` rows for *other* players survive with their own score/stats intact — only the deleted account's own attribution is severed. A genuinely dead row is also what makes "register again with the same email creates a new account, not a resurrected one" trivial: nothing to collide with, no soft-delete flag to remember to check everywhere else in the codebase. The action itself mirrors Fortify's own logout controller (`Auth::guard(config('fortify.guard'))->logout()`, `session()->invalidate()`, `session()->regenerateToken()`) before deleting, then redirects to `/`. Covered by three Feature tests (user gone + logged out + redirected; passkeys/hosted-room cascade vs. game-participant nulling; a real `POST /register` with the same email afterward succeeds and authenticates a different user id) plus the dialog's own open/cancel coverage in the same browser test file as Clear All Stats.
- Public profile privacy: an unknown username 404s, but a private profile that *does* exist still renders `200 OK` with a plain "This profile is private" message — deliberately distinguishable from "no such user," and matches how the owner viewing their own private profile needs to see a real 200 with their own stats, not a 404.
- Found the same Larastan/`casts()` inference gap twice (first on `FamilyFeudQuestion`, then here): `GameSession::type`/`GameParticipant::result` resolved to `string` instead of their enum types in one call chain (`$participant->gameSession->type->value` inside a `groupBy()` closure), even though `casts()` declares them correctly. Fixed with explicit `@property` PHPDoc annotations. Worth remembering as a recurring gotcha with this Larastan version.
- **Homepage: auth links moved into the top bar.** `welcome.blade.php` used to render "Create an account"/"sign in" (guests) or "Your dashboard" (logged in) as a plain text line below the game grid, with no logout button anywhere on the homepage. Moved into the shared button-bar's right side, matching every other page's convention: added a genuinely new `$barRight` slot to `layouts/app.blade.php` — deliberately a **plain** slot, not a `@teleport` target, since `welcome.blade.php` is a classic `@component`/`@slot` Blade view with no Livewire round trip that could ever go stale (contrast with `#game-actions`, which needs `@teleport` specifically because game pages *do* re-render). `welcome.blade.php` fills it with `@guest`/`@else`: Sign In + Create an Account (guest), or Dashboard + a real `POST /logout` form (authenticated). Also set the layout's existing (previously unused anywhere) `$manyButtons` flag on the homepage, tightening padding/gap at narrow widths for the now three-button row. **Blade gotcha hit while wiring `$manyButtons`:** `@slot('manyButtons')1@endslot` on one line rendered the literal text `1@endslot` onto the page — `@endslot` needs whitespace/a newline before it, not to be butted directly against preceding content. Verified via a scripted headless-Chrome (CDP) session (guest/authenticated states at desktop and mobile widths, no wrapping, logout round-trips correctly) since there was no prior JS/DOM behavior to assert on with Pest here; added `tests/Feature/WelcomePageTest.php`.
- **Dashboard: Edit Profile/Log Out buttons moved into the top bar** the same way, for the same "one consistent chrome convention across every page" reasoning as the homepage change above.

## Site-wide design system & chrome

Every earlier phase above was functionally complete on its own, but the front end was initially a Tailwind-utility *reinterpretation* of `legacy/*.css`'s design system rather than a faithful port, Boggle's word-building was a tap-per-die + Submit/Clear pair (not the real drag/pointer gesture), two whole legacy pages (`boggle-static.html`, `yahtzee-roller.html`) and the About page had never been built, and there was no consistent button-bar/site-footer/rules-dialog chrome across pages. This section covers that cross-cutting design/chrome work, plus every bug found in it since (several of which affected every game at once, not just the one being tested when they were caught).

**Design system port + drag gesture:**
- Ported `legacy/shared.css` + `legacy/boggle-shared.css` into `resources/css/app.css` near-verbatim as real CSS classes (full OKLCH token set, `.button-bar`, `.site-footer`, `dialog.rules-dialog`, `.setup`, `.option`, the fullscreen/chrome-hide system, Boggle's board/word-list panel classes), rather than Tailwind-utility reinterpretations.
- Rebuilt `layouts/app.blade.php` with a real button-bar (Home + optional Rules + optional fullscreen-toggle via named Blade slots) and site-footer, consistent on every page.
- Rebuilt Boggle's play page with the real pointer-capture drag/tap word-building gesture (`stepPath`/`nearestCandidateCell`/`processDragPoint`, diagonal-neighbor bias, coalesced-pointermove sub-stepping) via a `@script` block operating on client-only path state, submitting the finished word to a new `submitPath()` action in one round trip. The countdown timer moved from `wire:poll.1s` to a pure client-side `setInterval` — a per-second server round trip would let Livewire's morph clobber the JS-only `.selected`/order-badge state mid-drag. Deliberately not ported: the live "valid word in progress" dictionary check (would ship a second copy of the dictionary to the client) and JS-measured layout fine-tuning (CSS fallback values used instead).
- Added Boggle's group-play variant (`pages::boggle.group` at `/boggle/group`), the Yahtzee dice-only roller (`pages::yahtzee.roller` at `/yahtzee/roller`, pure Alpine, no Livewire round trips), the About page, and a fidelity pass on `welcome.blade.php`.
- Two real, previously-invisible bugs found while doing this pass (both silently broke color/sizing on **every** page using `bg-accent`, `px-*`, etc.):
  1. `@theme { --color-accent: var(--accent); }` silently failed to generate `bg-accent` (while `text-accent`/`border-accent` worked) — Tailwind v4 only partially resolves utilities from theme tokens that reference *other* runtime CSS custom properties unless the block is `@theme inline { ... }`. Every `bg-accent`-styled CTA site-wide was silently rendering as the plain surface color instead of accent blue until fixed.
  2. Cascade-layer priority, not specificity, decided the fight between new global `button {}`/`input {}` rules and Tailwind's own utility classes — an unlayered custom rule always outranks any rule inside a `@layer` regardless of specificity or source order. Fixed by wrapping the element-default rules in `@layer base`.
- Also worth remembering: a CSS `/* ... */` comment containing the literal substring `*/` anywhere in its own text closes the comment early and turns the rest into broken real CSS — surfaces as a cryptic `CssSyntaxError: Missing opening (` pointing nowhere near the actual cause.

**The `@teleport` button-bar bug (the single most-repeated bug class in this app's history):**
- **First discovery**: every dynamic button-bar button was permanently broken. Boggle's End Game/New Game toggle, Yahtzee's New Game button, Family Feud's Reveal/End Game/New Game — all originally passed through a `<x-slot:barRight>` on the *layout*, but a Livewire full-page component's AJAX round trip only ever re-renders and morphs the component's own root element; layout-level named slots are evaluated exactly once, at the very first full-page load, and never touched again. Confirmed empirically: after starting a game, the live DOM had zero "End Game" button. This shipped in the first pass because verification only ever drove the drag gesture and checked initial screenshots, never clicked the button-bar's own dynamic buttons afterward. Fixed with Livewire's `@teleport`: the layout exposes a stable, always-present anchor (`<div id="game-actions" style="display: contents;">`) inside `.button-bar .right`, and each game page teleports its own state-dependent button(s) into it from within its own component template — unlike a layout slot, this *does* participate in the component's normal re-render/morph cycle. Verified end-to-end via headless-browser automation for Boggle, Yahtzee, and Family Feud.
- **Second discovery, months later, while working on Yahtzee's fullscreen/spectator UI**: `.button-bar .right > button:not(#chrome-toggle-btn)` — the CSS rule meant to dim/hide every action button except the fullscreen toggle itself when chrome is hidden — used a `>` direct-child combinator, which **never matched a single teleported button, for any game, the entire time**. `@teleport` wraps its content in nested `display: contents` wrapper `<div>`s (`#game-actions` itself, plus `@teleport`'s own wrapper); `display: contents` only affects box generation for layout purposes — it flattens those wrappers out of the *rendered box tree* so their children look like direct flex items of `.right` visually, but the actual DOM tree (what a `>` combinator matches against) still has them nested two levels deep. Confirmed live (`element.matches('.button-bar .right > button')` returned `false` on a real teleported button) rather than assumed. This explained why Yahtzee's "Watch only"/spectate toggle never hid in fullscreen — and meant every other game's own action buttons had probably never actually dimmed in fullscreen either, silently, since the very first `@teleport` fix above. Fixed by removing the `>` in all three affected rules (the dimming rule, its `chrome-hidden` counterpart, and the `prefers-reduced-motion` transition-disabling rule), making them plain descendant selectors.
- **The one deliberate exception**: Yahtzee's `#scores-btn` (the mobile scoreboard drawer trigger) needed to stay visible/opaque through fullscreen mode specifically — a casting/TV device is exactly the scenario fullscreen mode is for, and checking the shared scoreboard without leaving fullscreen matters most there. Added `body.chrome-hidden .button-bar .right button#scores-btn { opacity: 1; pointer-events: auto; ...concrete values... }` — needed concrete values rather than a bare `revert`, since `@layer base`'s own `button` rule (where these values would normally come from) is a *layered* rule that never wins over this unlayered one regardless of source order. Its visibility then created a follow-on layout bug: `body.scrollable.chrome-hidden`'s padding-top shrink assumes nothing remains visible in the bar once fullscreen — with `#scores-btn` now staying visible by design, it visually collided with the status text beneath it. Fixed with `body.scrollable.chrome-hidden:has(#scores-btn) { padding-top: clamp(80px, 10vmin, 96px) !important; }`.

**Button-bar spacing:**
- No minimum gap ever existed between `.left` and `.right`'s own button groups — `justify-content: space-between` alone hands *all* leftover space to whichever gap is smaller, shrinking to zero (buttons touching) once both groups together are wide enough to fill the bar, which is exactly what started happening once Yahtzee's online-room work added two more right-side buttons on a narrow screen. Fixed with an explicit `gap: 10px` on `.button-bar` itself (and a smaller `6px` at the `max-width: 480px`/`.many-buttons` breakpoint), matching the existing internal button-to-button gap within each group so all three gaps read as one consistent rhythm.
- The "Rules" button's label was shortened to a bare `?` (`aria-label="Rules"` kept for accessibility) to save horizontal room on narrow screens — a global change in `layouts/app.blade.php` affecting every game's Rules button at once, not a Yahtzee-only tweak.

**Color misuse and other Round-3-era fixes:**
- **Accent-blue was overused** — `--accent` (the same bright, saturated blue as a selected Boggle die or a found word) had leaked onto page headings and generic "primary" CTA buttons that legacy never color-codes at all (legacy's buttons are always the same muted `--btn` tone; the only per-instance color legacy applies to a button is `option.active`'s *text*, not its background). Added a `--color-bar` Tailwind alias (`text-bar`/`bg-bar`) for genuine headings/branding, moved every heading-like use to it, stripped `bg-accent`/`text-accent` off buttons and transient status messages. Left `--accent` only where legacy's own convention uses it: selected-die/order-badge/`option.active` state, a found word, the controlling Family Feud team, a won game result.
- Fixed the dashboard username literally reading `@{{ auth()->user()->username }}` on screen — `@{{` is Blade's escape syntax for `{{ }}` (meant for JS template literals sharing a page with Blade); there's no such coexistence need here.
- The online-room code was shown in a `.heading`-classed `<div>`, and `.heading` carries `user-select: none` — never selectable/copyable by design of a class meant for page titles. Replaced with the readonly-input-plus-`[data-copy]`-button pattern already used for Boggle's challenge-share link.
- Copied the missing legacy static assets into `public/` (`manifest.json`, favicons, `og-image.png`, web-app-manifest images) — the layout's `<head>` had referenced all of these since the design-system port, but none existed, so every page 404'd on its manifest/favicon/social-share image. Added `public/sw.js` + registration — **not** a straight copy of legacy's service worker (which precaches a fixed list of static file paths that don't exist in this Livewire/Vite architecture); this one only cache-first's the fingerprinted `/build/*` Vite output (safe by construction — a new deploy always gets new filenames) and leaves every HTML response to the network, since caching a Livewire page risks serving a stale CSRF token or an unrehydratable `wire:snapshot`.
- Converted Yahtzee's scorecard and Family Feud's board/scoreboard/panel markup from generic Tailwind reinterpretations to legacy's actual classes/structure. Converted Boggle's setup/room/lobby pages to the same `.setup`/`.option`/`.option.active` classes used everywhere else.

**Low-stim confirm dialogs (`<x-dialog>`/`<x-confirm-dialog>`), replacing `wire:confirm`:**
- Family Feud's Skip Question/End Game/Reveal actions were the app's only remaining use of `wire:confirm` (native browser `confirm()`) — Boggle's and Yahtzee's own End Game/New Game buttons never had a confirmation at all, so `docs/TODO.md`'s earlier note describing all three games as using it was inaccurate and has been corrected. The passkey-removal dialog on `/profile` (`resources/views/pages/⚡profile.blade.php`) had already hand-rolled the *right* pattern once — a custom `<dialog>` styled like `.rules-dialog`, driven by vanilla JS, instead of `confirm()` — but as one-off markup + one-off `app.js` wiring with nothing to reuse.
- Generalized that pattern into two anonymous Blade components: `<x-dialog>` (the low-stim `<dialog>` primitive — muted `oklch()`-based backdrop matching `.rules-dialog`'s own, `js-dialog` class for its shared CSS, optional title) and `<x-confirm-dialog>` built on top of it (message + Cancel button + a named `confirm` slot the caller fills with whatever the actual confirming action is — `wire:click`, a form submit, anything). The `confirm` slot (rather than the component hard-coding what "confirm" does) is what lets the same component serve Family Feud's `wire:click="skipQuestion"` today and Edit Profile's clear-stats/delete-account actions next, without the component needing to know about Livewire at all.
- **Generic, delegated JS instead of one-off wiring per dialog.** `resources/js/app.js` gained a single `document`-level delegated click listener (`[data-dialog-open]` opens the target dialog by id, `[data-dialog-close]` closes the nearest ancestor `<dialog>`, a direct click on a `.js-dialog`'s own backdrop closes it) rather than binding listeners to specific elements at `DOMContentLoaded` the way the Rules dialog and passkey dialogs both do. That direct-binding approach only works because those dialogs are static, page-load-only markup; Family Feud's new confirm dialogs live inside Livewire-managed, conditionally-rendered markup (the Options panel, teleported action buttons) that gets morphed/replaced after almost every action — a listener bound directly to one of those elements at load time would silently stop working the first time Livewire re-rendered it. Delegating on `document` sidesteps that entirely.
- Confirm buttons carry **both** `wire:click` and `data-dialog-close` — clicking Confirm closes the dialog immediately, client-side, rather than waiting on the Livewire round trip to morph it away implicitly (which does also happen, since the dialog's `open` attribute isn't part of the rendered Blade output and morphdom would strip it, but relying on that felt like an implementation detail rather than an intentional close).
- Replaced all three Family Feud `wire:confirm` call sites (`revealManually`/`endGame`/`skipQuestion` in `pages::family-feud.play`) with a trigger button (`data-dialog-open`) plus an adjacent `<x-confirm-dialog>`, kept next to their trigger (rather than hoisted to one shared location) so each dialog's presence in the DOM tracks the same `@if` condition as its trigger's own visibility.
- Covered by `tests/Browser/FamilyFeudConfirmDialogsTest.php` (6 tests: each of the three dialogs opens on trigger click, Cancel closes it with no side effect, and Confirm actually performs the action) — the underlying game actions themselves were already covered at the Livewire level in `tests/Feature/Games/FamilyFeudGameTest.php`, so these are purely about the dialog's own open/cancel/confirm JS behavior. See "Automated browser testing" below for a real testing-infrastructure gotcha found while writing them (text-based `click()` hanging on an ambiguous match).

**Verification-process lessons worth keeping, cumulative across all of the above:**
- A "200 OK" smoke test proves a route resolves, not that the right content is on the page — the root `/` route served Laravel's unmodified default welcome page through several early phases' own docker verification before anyone actually looked at what came back.
- The `@teleport` bug (first discovery) existed through an entire "done" pass because verification checked *what renders*, never *what happens after a state-changing click on chrome that lives outside the component's own re-rendered root*. Any future layout/slot mechanism carrying Livewire-state-dependent content needs that specific check — render once, change state, click the thing again.
- The `@teleport` bug (second discovery, the CSS selector) went unnoticed for the entire time between the two discoveries because Pest-level tests (`Livewire::test()`) invoke component methods directly and never render real DOM/CSS at all — they can prove a button's *label* is correct after a state change, but nothing about whether it's actually visible, clickable, or positioned. The Yahtzee online-rooms pass repeated a milder version of the same mistake (see that section above) before switching to mandatory live-browser verification for anything UI/CSS-related. This app's new Pest browser-testing setup (Playwright-backed, see below and `CLAUDE.md`) exists specifically to start catching this class of bug automatically instead of relying on remembering to check by hand every time.

## Automated browser testing

Pest v5 (already this project's test framework) ships first-party browser testing support powered by Playwright, via the `pestphp/pest-plugin-browser` package — chosen over Laravel Dusk specifically because it's the same `Livewire::visit(...)`/`it(...)` syntax as every other Pest test in this suite (`php artisan test` runs both kinds together), rather than a separate PHPUnit-style test case class and a separate `php artisan dusk` invocation. See `CLAUDE.md`/`AGENTS.md` for the concrete setup (what's installed, where browser tests live, and when to reach for one instead of `Livewire::test()`) — that's the file kept current for "how do I write one of these," so it isn't duplicated here.

Also installed `pestphp/pest-plugin-agent` alongside it specifically to close the exact gap flagged during Yahtzee's online-rooms work above: an agent claiming a UI change works from reading the code, or from a Pest assertion that never touched real DOM/CSS, rather than actually checking. Its `--agent='...'` flag runs a one-off snippet (optionally driving a real Playwright browser via `visit(...)`) inside the project's real Pest configuration and reports a genuine pass/fail — a fast verification probe for mid-task use, not a replacement for a real test.

**First real coverage: Yahtzee, both local play and online rooms** (`tests/Browser/Yahtzee{LocalPlay,Mobile,RoomBrowser}Test.php`), 12 tests. Local play drives a full solo game start-to-"Game Over" through 13 real click→Livewire round trips (rolling then scoring whichever category is first pickable each round, since dice are real `random_int()` rolls with no deterministic target) and confirms a kept die's `.kept` class survives a second roll's re-render. Online-room coverage seeds a `Room`/`GameSession.state`/`RoomSeat` trio directly at the database level — the exact shape `pages::yahtzee.room`'s own `onRoomStarting()` writes — rather than driving two real logged-in browsers at once, and drives a single real seat's browser against that seeded state: hosting a room and joining one by code through the real setup-screen UI, a seated player rolling/scoring for real, an unseated visitor correctly landing in the read-only spectator view (no `#rollBtn` in the DOM at all, not just disabled), and the mobile scores drawer opening and staying open across a simulated `onStateUpdated()` call (standing in for a live broadcast, which `BROADCAST_CONNECTION=null` suppresses in the test env exactly as it does for `tests/Feature/Games/YahtzeeRoomTest.php`'s own manual-dispatch approach).

Two real, non-obvious limitations of `pestphp/pest-plugin-browser` v5.0.0 surfaced while building this out, both confirmed via the `--agent` probe before being designed around rather than fought:
- **Two concurrent `visit()` pages reliably hang** (30-60s+, had to be killed) the moment a content assertion (`assertSee`/`assertDontSee`) runs on one page followed by a fresh `visit()` for a second — reproduced identically whether the two pages were opened via two separate `visit()` calls or the array form (`visit([$url1, $url2])`), and independent of the session driver (`array` vs `file`). Plain concurrent visits with no login/assertions interleaved (`visit(['/', '/about'])`, immediate `assertSee` on each) work fine and fast, so this isn't concurrency itself failing — it's specifically that pattern of interleaving. Given `BROADCAST_CONNECTION=null` in the test env means no real broadcast would reach a second live browser during a test anyway, genuine two-simultaneous-browser multiplayer testing wasn't worth fighting for: every room test here uses exactly one real browser page plus DB-seeded state for "the rest of the room," mirroring the Feature test's own manual-dispatch approach.
- **`->on()->mobile()` silently drops every click.** Confirmed with the simplest possible case — a plain `<a><button>Home</button></a>` link with no Livewire involved at all still didn't navigate after `click('Home')` under `on()->mobile()`, with no exception thrown. `resize(width, height)` (also in the plugin's API) sets the same narrow viewport without touching device/touch emulation and clicks through it work identically to desktop, so every mobile-viewport test in this app uses `resize(390, 844)` instead of `on()->mobile()`.
- **A plain-text `click('Some Label')` hangs (not errors) the moment more than one element on the page contains that text — including a match inside a currently-closed `<dialog>` or an unrelated `<strong>` in the Rules panel.** Found while writing `FamilyFeudConfirmDialogsTest` (see "Low-stim confirm dialogs" below): `click('Options')` hung 60s+ because the Rules panel's own copy also contains the word "Options" in a `<strong>` tag; `click('Cancel')` hung the same way once a second confirm-dialog (closed, `display: none` via the UA default `dialog:not([open])` rule) existed elsewhere on the page with its own "Cancel" button. Unlike a genuinely ambiguous CSS *selector* — which Playwright rejects immediately with a clear "strict mode violation: resolved to N elements" error — a text-based click silently waits on whichever match it resolved to (sometimes the wrong, never-visible one) until the browser timeout, which reads as an indefinite hang with no diagnostic. No fix from the plugin side; every click in that test file targets a unique `id` instead of a label once more than one dialog/element can share the same wording.

Setup specifics: `composer require pestphp/pest-plugin-browser pestphp/pest-plugin-agent --dev`, `npm install playwright@latest --save-dev`, `npx playwright install chromium`. Added a `Browser` testsuite to `phpunit.xml` (mirroring `Unit`/`Feature`) and added `'Browser'` to `tests/Pest.php`'s existing `pest()->extend(TestCase::class)->in(...)` call — without that second part, a browser test has no Laravel app container bootstrapped at all and fails immediately with `Target class [config] does not exist.`, since (unlike `Unit`, which opts in per-file with its own `uses(TestCase::class, ...)`) `Feature` had been the only directory wired up globally. `tests/Browser/Screenshots` added to `.gitignore` (Pest's own convention for screenshot output). Seeded with two real tests, not placeholders: `YahtzeeRulesDialogTest` (opens/closes the rules `<dialog>` via a real click and asserts visible text before/after — directly the same class of bug as the scoreboard-dialog's `[open]`-scoping bug above, just guarding a dialog that never actually broke) and `HomepageSmokeTest` (`assertNoJavaScriptErrors()`/`assertNoConsoleLogs()`, plus guest auth-link visibility) — full suite confirmed green together (`php artisan test --compact`, 262 tests) and the `--agent` probe confirmed working with a real one-off snippet before calling this done.
